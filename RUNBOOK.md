# Runbook — Grim Dawn Companion Tool

Master plan for building the tool in independent, verifiable stages. Each stage is sized for one focused Claude Code session.

## How to kick off a stage

In a fresh Claude Code session, say:

> Read RUNBOOK.md and implement stage N per its plan in docs/plans/. Verify against the acceptance criteria before finishing.

Each stage plan is self-contained (goal, format facts, deliverables, acceptance criteria, verification commands). After a stage passes verification: tick its box below, commit, and note deviations in an "Outcome" section at the bottom of the stage plan.

See the plan's Outcome.
- [x] **Stage 5A.2 — Item requirements & character attributes** — [docs/plans/stage-05a2-requirements.md](docs/plans/stage-05a2-requirements.md)
  Attribute requirements are **equation-derived, not stored**: `itemCostName` → `records/game/itemcostformulas*.dbr`, evaluated at `itemLevel` per slot class (spears ride `melee2h`; medals require nothing); level gates are explicit and affix-inclusive (`max(base, prefix, suffix)`); `-% Requirement` reductions are a scope × attribute matrix. Aggregate gains attribute totals (save base + mastery bars + gear ± %), OA/DA contributions, and `checkRequirements`.
  Gate: **every equipped item on both characters passes the check** — and the first run failed it, catching a real bug (jewelry's `totalAttCount` stat count inflated by non-stat keys). See the plan's Outcome.

- [x] **Stage 5A.4 — Wielding modes, set duplicates, engine caps** — [docs/plans/stage-05a4-wielding-and-caps.md](docs/plans/stage-05a4-wielding-and-caps.md)

- [x] **Stage 5A.5 — Damage-type path** — [docs/plans/stage-05a5-damage-path.md](docs/plans/stage-05a5-damage-path.md)

- [x] **Stage 5B — Context document builder** — [docs/plans/stage-05-context-builder.md](docs/plans/stage-05-context-builder.md)

- [x] **Stage 6B — Unread containers, component semantics, advice legibility** — [docs/plans/stage-06b-advisor-feedback.md](docs/plans/stage-06b-advisor-feedback.md)
  All six parts landed. **`reagents.gst` is `transfer.gst`'s format with the entries wrapped in nested blocks** (id 0, like a stash sack) — two non-advancing reads per entry is the whole desync, and block 20 now checksums. It was cracked by inverting the search: rather than guessing header variants, solve for the state a known plaintext forces (`state = rawU32(o) ^ n` for a record path of length `n`), which found all 61 entries in one pass. `potions.gst` came free; `transmutes.gst` stays out of scope. **The store keeps rows at quantity 0** — a "have held this" marker that would have read as one on hand, since every consumer floors `stackCount` at 1; dropping them turned "missing Manticore Eye 1/9" into the true `0/9`. Materials went from `Royal Jelly ×6` to eighteen kinds. The plan's caution about levels-per-point paid off: the game *does* state it (`playerlevels.dbr` — 1 point per level, 8 attribute per point), so §12's arithmetic is derived, not folklore (`GameDb.levelProgression()`, schema 10). Three deviations, all in the plan's Outcome — **§8 became the single component list** (owned, installed *and* craftable, with stats) and §10 narrowed to relics, **reagent chains resolve transitively** (`Haunted Steel` is *craftable now, after first crafting 3× Vengeful Wraith*, not *missing*), and the iron bill excludes the one-off priciest craft so 1.3M reads as "not a constraint". The repair loop keeps whichever answer is cleaner rather than trusting the revision — and both branches fired live: run 1's revision was no better and the original was shown, run 2's went **1 warning → clean**. Gate: **not one number in §3 moved** — the only diff is two reworded sentences, because the granted-buff hop is named and shown, never summed.
  Follow-on from the user's review of the first live `advise` runs. **`reagents.gst` (block 20) — the shared crafting-material and component store — has never been opened**, which is why every loose component reads `[inv]` and the materials line says "Royal Jelly ×6"; the envelope is verified and four hypotheses are already ruled out in the plan, so the next session starts from a lead, not from scratch. Plus: loose components print no stats, `Grants: <skill>` never follows the buff hop, the per-copy buff stacking rule is unstated, §10 narrows to components + relics, the on/off-type note names its evidence instead of reading as a verdict, every stat reference gets `Resistance`/`Damage` (a mechanical `ambiguous-stat` check, since `+99% Pierce` and `+22 FCL` meant different things four words apart), the CLI renders its own `Slot | Current | New | Action` table from the structured plan, and `checkPlan`'s warnings get fed back for exactly one revision. Two more from the same review: **a dual-wield enabler from an invested mastery passive is permanent and survives every gear change** — the dossier names all three of `_Suchka`'s but flattens them into one list, and the advice duly kept a relic "for the Bloodbath enabler" that two learned passives already made redundant; and iron budgeting becomes conditional on a computed verdict rather than always-on, since 35,500 against 1,315,676 is noise (it stays loud for a genuinely poor character). Finally a **twelfth section, the "unlock ladder"**: the HOLD data already knows that nine of `_Suchka`'s twelve held items unlock at level 84 and that three attribute points into Spirit buy one more, but it reads as twelve unordered rows — §12 groups by shared threshold and does the `ceil(deficit / 8)` arithmetic so "spend your next 3 points on Spirit" becomes a stated move. (Note: this takes the document past Stage 5B's "eleven sections" gate — `test/context.test.ts:374` asserts the old count and must be updated, not worked around.)

- [x] **Stage 6C — Throughput, stable ids, and a structured answer** — [docs/plans/stage-06c-throughput-and-structured-answer.md](docs/plans/stage-06c-throughput-and-structured-answer.md)
  Second follow-on from the live runs. **Attack speed is attacks-per-second and additive**, not a percentage: the player record holds the baselines (1.25 attack, 1.25 cast, 0.93 run) and a weapon's `characterBaseAttackSpeed` shifts the attack rate by −0.24…+0.01 — so `1.99` on a weapon is the game's `{%.2f} Attacks per Second` display, never "199%". Only weapons carry the term (checked every other class); the char sheet's percentage is the resulting rate over the baseline with the cap on *that*, which is what the game means by "slower weapons gain less from % Attack Speed bonuses". `_Suchka` reads **177% → 182% buffed (2.27/s) with 19 points of headroom**, and **movement already 15 points past its own raised 138% cap** — the two facts both live runs said in as many words that they could not compute. **Cunning and Spirit do scale damage** and the game's attribute descriptions say which (Cunning: Physical/Pierce/Bleeding/Internal Trauma; Spirit: the magical types; Physique: none) — but the *rate* is engine-side like the armour hit weights, so §3 names the direction, refuses to invent a coefficient, and states outright that a swap moving an attribute by tens of points against a total in the hundreds must not block the move. Also: **194 components and augments got dossier ids** from the same hash as items, which retires `verify.ts`'s strip-the-parenthetical name matching and adds `name-mismatch` (a right name on a wrong id is the failure an id-only plan hides); the plan schema gained `summary`, `keyMoves`, `projected` and per-verdict `itemName`/`targetId`/`targetName`; `verdictRows` finally carries `gains`/`costs`, which is why the first table showed a `+12% Fire Resistance` move as having no benefit; and `advise --json` writes one envelope for Stage 7. The user's "split prose and JSON into two calls" was **measured and rejected** — the JSON is 2.7k of ~30k output tokens (~$0.20 of a $3.70 run), a second call costs more on Opus and saves 4% on Sonnet, and an extractor without the dossier cannot resolve ids at all. What *was* duplicated: the model wrote a per-slot table and the CLI rendered its own, so the terminal printed it twice — the prompt now forbids the prose table and `--out` appends the rendered one. Gate: **§3 and §4 diff to 18 added lines and zero changed ones** — speed and attribute scaling are purely additive. Live run: 5 warnings → one revision → **clean**, 18 verdicts with 18/18 `itemName`, 16/18 `targetId`, 3 `keyMoves` (2 calls · $4.16 · 845s). Where Stage 6 wrote *"the dossier gives no attack-speed total, so I cannot say whether you were at the 200% engine cap"*, this run wrote *"177% → 172% permanent, 177% with buffs, headroom widens from 19 to 28 modifier points — a real ~2.8% throughput cost"*.

- [x] **Stage 7A — Electron shell + character window** — [docs/plans/stage-07a-electron-shell-and-character-window.md](docs/plans/stage-07a-electron-shell-and-character-window.md)
  The read-only half of the app, split three ways like the 5A series. Electron + React shell at 1920×1080; **a current → proposed loadout comparison** (one row per slot: what is equipped, an arrow, what the advisor proposes, with component and augment as their own faces underneath), stats/resistances panel, inventory + stash + transfer + materials tabs, context-document-identical item tooltips. Core gains `ItemPosition`, `getIconInfo` (cell footprints come from icon size — they exist nowhere else), `grid.ts`, `session.ts` (the CLI's `contextFor` promoted to core) and `view.ts`'s `UiSnapshot` builder; the full IPC contract including the advise channels 7B implements.
  **Two plan decisions were reversed after the user reviewed the first build, and both were right to reverse.** The game's own `UI.arc` chrome was built, worked, and was dropped — that art is cut for the engine's fixed layout, so at the app's sizes it overlaps and fights the content; item icons carry information, frames were decoration bought with legibility. And the in-game **paper doll went with it**: its arrangement exists to wrap a rendered character, and there is none here, so the layout spent its middle third on nothing. What replaced it is the thing the tool is actually for — worn beside proposed, slot by slot, with **hovering a proposal lighting that item up wherever it lives** and clicking flipping the container panel to the tab holding it. That presentation reads `AdviseEnvelope` exactly as Stage 6C defines it, so 7B supplies data and changes no UI; today `getLastAdvice` answers `null` and the proposal column reads *locked*, which says what the app does better than a hidden column would.
  Verification moved to **Storybook + Playwright** at the user's suggestion (`npm run storybook`, `stories:shoot`, `stories:check`) against a *synthetic* fixture — a real snapshot is game-derived and uncommittable, and invented data makes the screenshots deterministic. Gate: stats match `aggregates` line for line; the context document is **byte-identical** (the id-stability proof the advice join needs). The in-game inventory comparison was impossible here (CrossOver + TCC), so the bag constants were settled from the data and came out stronger: `_Suchka`'s main bag tiles **96 of 96 cells with zero overlaps**, the game's own extra-panel texture is 258×259 = exactly 8×8 cells, and across both characters not one item overlaps or falls outside a grid — a joint proof of the icon-derived footprints and the save-derived coordinates. See the plan's Outcome.
  Two further review passes followed. The second was mostly legibility (Inter over Montserrat because nearly every glyph is a number in a narrow column; damage-type colour on stat lines; three responsive columns; the template class humanised for the UI but *never* for the document). The third fixed the one place the UI was still describing the game wrongly and added the piece of contract that was missing. **Armour said the character-wide `+482` in a note between the body parts and Absorption**, which invited exactly the reading it got — it is `(piece + flat) × (1 + %)` *per part* and has nothing to do with absorption, so it moved onto the heading. **A socket move is a proposal, not a note**: four of the seven verdicts keep the item and change what it carries, and they were rendering as the words "ADD-COMPONENT Seal of Might"; they now render the socketable itself, with its stats, and — for an extraction — what it destroys, which needed `UiSnapshot.socketables` (the dossier's 194 socketables by id) because a *proposed* component is installed nowhere and has no host to be read off. Also: the model's own `answer` finally has a tab, through a hand-written markdown tokenizer whose every leaf is text — so an answer cannot inject markup into the window by construction rather than by escaping, which is why 7B's planned `react-markdown` dependency is now unnecessary. And a **second, standing mark** beside the hover highlight, holding every item the plan asks you to act on: without it, finding the six that matter in a stash of two hundred means hovering the advice table row by row. 307 tests, 56 story assertions, context document still byte-identical.
  A fourth pass took the socket proposal one step further and fixed the one thing that was wrong in the *advice* rather than in the window. The proposal for a socket move is now **the same item rendered again with its new socketable in it** — the reader's question is "what will this slot look like", and a lone component makes them assemble the answer themselves; the consequences (the old component destroyed, the host an extraction destroys, the soulbinding) live in that item's tooltip, where someone hovering a proposal will look for them. And **`HOLD` was being used as a status**: §12 lists every candidate that fails a requirement so a threshold can be costed against what it unlocks, and the model read that as a to-do list, holding over-levelled items that lose to what the character is already wearing. A hold now has to say which slot it is for, what it displaces and what it wins by — prompt, schema and a new `unjustified-hold` check — because "cannot equip this yet" is a fact about an item, not a recommendation. Also: the whole item face is a hover target rather than its icon (both listen on `mouseover`, which bubbles, so icon → chip → name re-asserts the right tooltip at each step), and the window sizes itself against the **work area** rather than the screen, since a 1920×1080 monitor has already spent rows on the menu bar and Dock. 314 tests, 61 story assertions. Asked whether the Rainbow Filter's palette could be reused: **no, and there is nothing to reuse** — it is MIT but emits Grim Dawn's own `^` letter codes, whose RGB table is in the engine binary; the shipped text marks every damage type with the same generic `{^S}`.
  A fifth pass caught the same HOLD mistake one layer up: the **tooltip** was rendering a level gap as `needs level 84 (HOLD until then)` on 44 of `_Suchka`'s stashed items with no advice run in sight. That phrasing belongs to the context document, where it tells the *advisor* not to reject a candidate over a deficit levelling will close; addressed to the player it was a recommendation the tool had not made. It now states the gap and nothing else. The container mark became **typed** at the same time — equip / hold / destroy in three colours, because one green flag for all three turns a stash of things to wait for into a stash of upgrades — and the six **damage-over-time twins** got their own shade of their parent's colour: they convert together but cap and resist separately, so `+30% Burn Damage` painted exactly as Fire hid a real distinction. Names verified against the game's own `tagCharStats*` strings and checked over all 1131 distinct stat lines the character can reach; Bleeding stays alone, having no twin. 320 tests, 66 story assertions.
- [x] **Stage 7B — AI advice integration** — [docs/plans/stage-07b-advice-ui.md](docs/plans/stage-07b-advice-ui.md)
  The advise pipeline in the window: typed `AdviseEnvelope` in core (replacing the CLI's inline `--json` literal), per-character advice persistence, main-process run manager (honest phase progress + cancel over the ~500 s call; survives renderer reloads), the answer in the advice panel (summary, key moves, verdict table, cost line; full markdown answer on its own tab), and advice painted onto the gear — a typed badge per item, counts on tabs holding items you cannot see, an action tooltip beside the base one. Advice ids join against the live snapshot and stale ones are listed by name, never silently dropped.
  Gate: `advise --json` **byte-identical** before and after moving to `buildEnvelope` (same run through the mock provider, diffed with the timestamp masked); 346 tests; 150 story assertions; 13 assertions driven through the real Electron window by the new `npm run app:check` — which covers the seam neither Storybook nor vitest can reach (the preload bridge, the nine IPC channels, the run manager, the advice file).
  **Live run for the record**, started from the window's own button: **2 calls · opus/high · 210,627 in · 64,878 out · $3.78 · 12m 03s**, `asking the model` at 0 s → `revising the plan` at **598 s** → answer at 723 s, **2 `ambiguous-stat` warnings → one revision → clean**. 14 verdicts (9 BUY-AUGMENT, 2 RE-AUGMENT, 1 EQUIP, 2 KEEP), 3 holds, **13 sells**, 5 key moves, 16 items marked on the live grid. The plan's finding was that *nine augment slots are empty and the three that are filled all carry Wight Skin Powder, pouring 45 points into an Aether resistance already 74 over cap* — and the sheet's projection column carries the consequence (Pierce 87 → 129, Fire 74 → 122, Bleeding 38 → 78, **Aether 154 → 109**, the over-cap resistance being spent rather than lost). Thirteen sells is also what settled the `sell` mark: without it those thirteen items would have carried no mark at all.
  **Two plan decisions were forced by the compile-time boundaries the earlier stages built.** Persistence could not live in `envelope.ts` as planned — that module is in the renderer's type graph, which compiles with `types: []`, so a `node:fs` import there is a compile error rather than a convention, and the split into `advice-store.ts` is what preserves the guarantee. `lucide-react` was dropped for nine hand-drawn `<path>`s on the zero-dependency rule (7A had already declined `react-markdown` the same way), and the plan's **blue for socket moves** went with it for a better reason than bundle size: a socket verdict's subject is the item you are *wearing*, and worn items are not in a container, so that colour had nothing to colour.
  **The run manager turned out to be the testable part, not the untestable one.** `src/main/advise.ts` imports nothing from Electron, so cancel-by-id, a refused second run, a stale cancel *not* killing the live run, a dead backend explaining itself, and a failure that survives a renderer reload are all ordinary unit tests against an injected provider — the same seam `claude-cli` gives its `spawn`, and for the same reason: every one of those is *timing*, and none can be tested against a real eight-minute subprocess. `SessionState` now keeps the `CharacterSnapshot` the UI was built from, so a run asks about **the document the window is showing** rather than one recompiled from a save the game may have rewritten in between.
  **The advice panel beside the item panel turned the floating layer from one child into two, and every consequence of that was a bug.** The wheel died over the panel (it takes pointer events and is portaled to the body, so it reached neither the panel nor the pane it covers) — a tall panel now scrolls itself and a spent one forwards the delta to the pane the card lives in, easing a mouse notch the way Chromium does while passing a trackpad gesture through 1:1, because easing that puts the scroll four frames behind the fingers. Two panels of different heights made the row's own box taller than the shorter one, so the empty ground beside it was an **invisible hover target** the tooltip refused to close from; the layer now takes no pointer events and each panel takes its own. A **200 ms** delay before a panel appears (220 ms before it goes) — first drafted as cold-open-only with instant switching afterwards, reverted on review because the two cases felt like different controls and brushing a component chip on the way to the panel still flashed it. And the **highlight follows the panel rather than the pointer**, which exposed that the loadout's worn card had never been wired for the highlight class at all, and that a socket-move row lit *both* its cards — the proposal is the same item with the same document id, so the row now remembers which side was pointed at.
  Also: `ActionKind` gained `sell` (the plan's `sell[]` had nowhere to go and was silently unmarked; red for both destroy and sell would merge an extraction that *spends* a host with a judgement that an item is not for this build), the corner flag grew a glyph because four colours in a stash of two hundred items stops explaining itself, and `actionMarks` is now derived from `adviceMarks` so the badge, the colour, the tab counts and the action tooltip are four views of one reading of the plan. A story caught that the **fixture's EQUIP verdicts carried no `gains`, `costs` or `reason`** — only their rendered rows did — which is an envelope no run can produce, since `verdictRows` is derived from exactly those fields.
  One environment trap, recorded because it costs an hour: this shell exports `ELECTRON_RUN_AS_NODE=1`, which turns the Electron binary into plain Node, so `require('electron').protocol` is undefined and the main process dies before it runs a line. `env -u ELECTRON_RUN_AS_NODE` is the fix.
  **A review pass after the live run changed six things, and four of them were the run telling us what the plan could not say.** (1) `fits` on a verdict: one verdict per slot has one name, and an item holds a component *and* an augment in independent sockets — the Neck `EQUIP` argued in prose for a Dread Skull and a Sagethorn Powder and carried neither, and `projected.notes` said so out loud (*"two free component fills … are not separate verdict rows"*). (2) `nextLevels` was in the schema and rendered nowhere, so two "skip this" recommendations existed only in prose. (3) The plan block was printed twice — once as the Plan tab and once as 17k of raw JSON at the end of the Full answer; `answerProse` strips it by *parsing* the trailing block rather than by its info string, because `parseAdvice` accepts a bare fence and any code block an answer ends on would otherwise be eaten. (4) Thirteen sells and no way to see them: the mark became a **flat ring plus a tint** (a corner flag is 11 px in a 32 px cell in a grid of two hundred) with **sell red and destroy violet**, off the traffic light because spending a host in an extraction is not a point on a scale of urgency. The ring's first draft had a glow and every marked cell then read as *highlighted*, which is the distinction the two marks exist on either side of. (5) The container legend became the control for its own count — hovering "sell or salvage 13" lights those thirteen, scoped by *kind* so it cannot light the loadout proposal naming the same item. (6) `Refresh` and `Run advice` now say in a tooltip what they do to a run in flight and to the stored answer, which was the actual question.
  **And three that make a stored answer safe to keep.** The envelope records `worn` — the loadout it was written against — and the panel splits the comparison in two, because **acting on the advice is what makes the loadout differ from it**: a single staleness bit calls the answer stale as its reward for being followed, and the design that suggests itself next (drop the stored run on a mismatch) deletes a twelve-minute answer at the moment the user does what it says. `applied` verdicts are reported in green and struck through; moved slots are named in amber. Runs are therefore **kept rather than overwritten** (`advice/<character>/<timestamp>.json`, a picker once there are two, `Clear` for the one on screen) — at four dollars each, taking a second opinion must not be a decision to destroy the first answer.
  **The one thing the backend turned out to be able to tell us:** `--output-format stream-json --include-partial-messages` streams the reasoning and the answer, and the last line is the *same* result envelope `json` prints on its own — so this is a change to the invocation, not to the parsing. The phase label says "asking the model" for ten minutes either way and cannot distinguish a working run from a wedged one. Coalesced to four pushes a second with a 600-character tail in a fixed-height box; written tokens, never a percentage. 369 tests, 181 story assertions, 14 app assertions.
  **A second review pass, and the two findings in it were both about identity.** (1) **An item's document id includes its attachments** — `itemId` hashes the component's and augment's names and seeds along with the base — so carrying out an `ADD-COMPONENT` changes the worn item's id without changing the item, and the first drift check reported that as *"Feet now holds Bloodhound Greaves (was Bloodhound Greaves)"*: useless, and the opposite of the truth. The envelope now records `wornSockets` beside `worn`, `loadoutDrift` classifies a moved slot as an item change or a socket change, and a socket move counts as **done** when the socketable now installed is the one the plan named. (2) The **full ring** the container mark had become was reported as looking "always highlighted" within a minute of being shown — and that was right for a reason worth writing down: a border around a cell is how this window says *this one*, so sixteen standing marks cannot borrow that vocabulary, and dimming it does not help because the problem was never brightness. **A border is a state; a bar is an annotation.** The mark is now a bar along the bottom edge, an edge the highlight never uses.
  Also, from the same pass: the drift notices moved to the **top of the Loadout pane** with a bordered `DONE`/`CHANGED` stamp per slot (a glyph and a word — the glyph is recognisable in an 84 px column, the word settles which of the two it is); the run picker and `Clear` are in the **header** as well as the panel, because the panel scrolls with the loadout and can be entirely off screen while the marks it produced are still on the gear; the hover panel is **centred** on its subject rather than left-aligned, so a marked item's panel no longer sits somewhere different from an unmarked one's; the expensive and destructive buttons explain themselves in the **window's own panel with no `title`**, since keeping both put the OS's box on top of ours a second later; and the streamed reasoning is kept **whole and collapsible** rather than as a 600-character tail — *"why did it decide that"* is a question the finished answer routinely raises and does not answer. 372 tests, 193 story assertions, 14 app assertions.
  **A third pass was about the two run controls, and it deleted more than it added.** `Clear` **deleted the run it sat beside** — which put a four-dollar answer one click from gone under the very button a reader reaches for *after acting on the plan* ("I have done these, ask me again"). It is now `New run`: it selects nothing, destroys nothing, and brings the Run button and the question box back with it. With an answer on screen there is no **Re-run** at all, because a second opinion costs eight minutes and does not replace the answer beside it, so asking again is two steps on purpose. And the window **opens on the empty state**, with the picker as the door and the number of kept answers stated in the panel — reopening last week's plan on launch put its marks on the gear before the reader had asked for them. Two IPC channels went with all that (`getLastAdvice`, `deleteAdvice`): `getAdviceHistory` → `getAdvice` is now the whole path in, and nothing in the window deletes a run. A re-read deliberately neither opens nor closes one — `load()` fires on every window focus, and dropping the open plan there would take the marks off the gear at the exact moment the user came back from the game to compare them. Also from that pass: the three button tooltips were **rewritten out of the app's own vocabulary** (no dossier, no envelope, no item database — `check-stories.mjs` asserts their absence), every control in a toolbar row is **one 30 px height** with its label centred by a flex box rather than by padding, and the streamed reasoning finally got a **story of its own** — it had one in the workspace, where the advice panel sits under a fourteen-row loadout and the transcript falls off the bottom of a 1080 screenshot, which is as much use as no story at all. 372 tests, 218 story assertions, 21 app assertions.
  **A fourth pass came out of the first weekend of live use** (thirteen items of feedback; details in the plan's Outcome). The run picker moved to the header alone, renders whenever any run exists — hiding it "when there was nothing to choose" once stranded a single open run with no way back — and leads with `New run` as a real entry. The streamed transcript became **reasoning-only** (the answer's own text was burying it, twice per repaired run; its progress is now the token count). The plan became **exhaustive over the carried bags and silent about the stash by rule**: §7 names even the unranked bag junk by id, and `checkPlan` gained `unaddressed-item` and `sell-in-stash` so the repair loop enforces both. A header **stash toggle** (persisted; CLI `--no-stash`) narrows the dossier to what the character carries. Plus: next-level unlocks are click-to-reveal, loose components state their use-on, absorption qualifiers render as one line, and the container tabs + legend are sticky. 379 tests, 227 story assertions, 24 app assertions.

## Post-v1 backlog (not planned in detail yet)

- ~~Own `.arz` parser backend~~ / ~~`.arc` reader~~ / ~~drop the last download~~ — **all done**, across Stages 3–4 and the follow-on after Stage 4. The tool now reads only the installed game and makes **no network requests at all**.
- **Grammatical agreement in gendered locales.** The text files encode declension: a noun opens with the gender it *is* (`[ms]`, `[fs]`, `[ns]`, `[np]`), an adjective spells out every form it *could take* (`[ms]искусный[fs]искусная[ns]искусное[np]искусные`), and the engine matches them. `cleanText` currently keeps the first form, so Russian reads "искусный печатка" where the game says "искусная печатка". Doing it properly means carrying the base item's gender on `DbItem` and picking the affix variant in `resolve.ts` — ~25 lines, affects 365 adjectival tags, and nothing at all in English.
- **Mod support.** With text and icons both coming from `.arc`/`.arz` files, a mod's `mods/<name>/database/*.arz` + `resources/*.arc` would slot into the same merge (the save files already record which mod they belong to). Untried; the Crucible (`survivalmode`) is the only mod installed here.
- **Ascendant Altar: ascension advice (gdx3).** Awakening is deterministic and *is* wired into stages 5A/5B (recipes carry reagents; "awakened version exists" is a HOLD signal). Ascension is not: `ItemAscensionFormula` rolls a random ascended affix from per-slot tables (`affixWeight`/`masteryWeight` 600/400) for five material types + 250k iron, with reroll formulas on top — advice richer than "it exists and is a gamble" (e.g. EV reasoning over the slot's affix table, themed swap lists in `ascensionaffixswaplists/`) is deliberately deferred.
- **Aggregate fidelity round 2:** count item-granted skills (`itemSkillName` actives/procs) and item skill modifiers (`modifierSkillName<N>`) in the aggregates — Stage 5A names both but sums neither. Also: model `Skill_Transmuter` as the skill-rewriting mechanic it is rather than banding it like a modifier, and extend the damage profile / armour / non-damage-resistance figures past permanent sources. (+skills rank boosts were promoted into Stage 5A scope during the 2026-08 plan review, and effective ranks are computed there.)
- ~~Conversion-aware damage ranking~~ — **done** (Stage 5A.5): global conversion and armor piercing fold into the flats, skill-scoped conversion is typed per skill. The true remainder: a full per-skill DPS model (folding `% weapon damage` inheritance, attack speed and crit into one number per skill) stays a non-goal — the profile answers *fit*, not DPS. (The speed half of that is now **done** in Stage 6C: `aggregate.speed` resolves attack/cast/movement against the caps.)
- **The attribute → damage coefficient.** Stage 6C established *which* types Cunning and Spirit scale, from the game's own attribute descriptions, and that the **rate is in no record** — so §3 states the direction and refuses a number. Recovering the rate would mean measuring it in game (vary one attribute, read the char sheet's `+% damage` line) and pinning it the way the armour hit weights are. Worth doing only if an advice run is ever seen to turn on it; today the rule "a shift of tens against a total in the hundreds is not a damage argument" covers every real case.
- OpenAI provider behind `AdvisorProvider` (settings toggle) — registered as a stub since Stage 6; `available()` is false and `advise()` explains itself.
- **Measure `xhigh` against `high` on the same dossier.** Stage 6 deferred it: at ~8 minutes and ~$1.50 a run the experiment currently costs more than it informs, and `high` showed no reasoning gap. Worth doing once the answers have a baseline to diff against.
- **`transmutes.gst` (block 19, 36 KB)** — illusionist/transmuted appearances. Envelope verified alongside `reagents.gst` in Stage 6B's investigation; deliberately out of scope there because appearance is cosmetic and changes no advice.
