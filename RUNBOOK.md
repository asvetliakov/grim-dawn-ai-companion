# Runbook — Grim Dawn Companion Tool

Master plan for building the tool in independent, verifiable stages. Each stage is sized for one focused Claude Code session.

## How to kick off a stage

In a fresh Claude Code session, say:

> Read RUNBOOK.md and implement stage N per its plan in docs/plans/. Verify against the acceptance criteria before finishing.

Each stage plan is self-contained (goal, format facts, deliverables, acceptance criteria, verification commands). After a stage passes verification: tick its box below, commit, and note deviations in an "Outcome" section at the bottom of the stage plan.

- [x] **Stage 5A.2 — Item requirements & character attributes** — [docs/plans/stage-05a2-requirements.md](docs/plans/stage-05a2-requirements.md)

Aggregate gains attribute totals (save base + mastery bars + gear ± %), OA/DA contributions, and `checkRequirements`.
  Gate: **every equipped item on both characters passes the check** — and the first run failed it, catching a real bug (jewelry's `totalAttCount` stat count inflated by non-stat keys). See the plan's Outcome.

- [x] **Stage 5B — Context document builder** — [docs/plans/stage-05-context-builder.md](docs/plans/stage-05-context-builder.md)

The plan's 30k budget turned out to be a *floor*, not a ceiling — the whole reachable candidate set costs ~36k, so the default is now 100k and the gate is a safety net for oversized stashes rather than a target. - [x] **Stage 6 — AI provider + advise** — [docs/plans/stage-06-ai-advise.md](docs/plans/stage-06-ai-advise.md)

- [x] **Stage 6B — Unread containers, component semantics, advice legibility** — [docs/plans/stage-06b-advisor-feedback.md](docs/plans/stage-06b-advisor-feedback.md)
  All six parts landed. **`reagents.gst` is `transfer.gst`'s format with the entries wrapped in nested blocks** (id 0, like a stash sack) — two non-advancing reads per entry is the whole desync, and block 20 now checksums. It was cracked by inverting the search: rather than guessing header variants, solve for the state a known plaintext forces (`state = rawU32(o) ^ n` for a record path of length `n`), which found all 61 entries in one pass. `potions.gst` came free; `transmutes.gst` stays out of scope. **The store keeps rows at quantity 0** — a "have held this" marker that would have read as one on hand, since every consumer floors `stackCount` at 1; dropping them turned "missing Manticore Eye 1/9" into the true `0/9`. Materials went from `Royal Jelly ×6` to eighteen kinds. The plan's caution about levels-per-point paid off: the game *does* state it (`playerlevels.dbr` — 1 point per level, 8 attribute per point), so §12's arithmetic is derived, not folklore (`GameDb.levelProgression()`, schema 10). Three deviations, all in the plan's Outcome — **§8 became the single component list** (owned, installed *and* craftable, with stats) and §10 narrowed to relics, **reagent chains resolve transitively** (`Haunted Steel` is *craftable now, after first crafting 3× Vengeful Wraith*, not *missing*), and the iron bill excludes the one-off priciest craft so 1.3M reads as "not a constraint". The repair loop keeps whichever answer is cleaner rather than trusting the revision — and both branches fired live: run 1's revision was no better and the original was shown, run 2's went **1 warning → clean**. Gate: **not one number in §3 moved** — the only diff is two reworded sentences, because the granted-buff hop is named and shown, never summed.
  Follow-on from the user's review of the first live `advise` runs. **`reagents.gst` (block 20) — the shared crafting-material and component store — has never been opened**, which is why every loose component reads `[inv]` and the materials line says "Royal Jelly ×6"; the envelope is verified and four hypotheses are already ruled out in the plan, so the next session starts from a lead, not from scratch. Plus: loose components print no stats, `Grants: <skill>` never follows the buff hop, the per-copy buff stacking rule is unstated, §10 narrows to components + relics, the on/off-type note names its evidence instead of reading as a verdict, every stat reference gets `Resistance`/`Damage` (a mechanical `ambiguous-stat` check, since `+99% Pierce` and `+22 FCL` meant different things four words apart), the CLI renders its own `Slot | Current | New | Action` table from the structured plan, and `checkPlan`'s warnings get fed back for exactly one revision. Two more from the same review: **a dual-wield enabler from an invested mastery passive is permanent and survives every gear change** — the dossier names all three of `_Suchka`'s but flattens them into one list, and the advice duly kept a relic "for the Bloodbath enabler" that two learned passives already made redundant; and iron budgeting becomes conditional on a computed verdict rather than always-on, since 35,500 against 1,315,676 is noise (it stays loud for a genuinely poor character). Finally a **twelfth section, the "unlock ladder"**: the HOLD data already knows that nine of `_Suchka`'s twelve held items unlock at level 84 and that three attribute points into Spirit buy one more, but it reads as twelve unordered rows — §12 groups by shared threshold and does the `ceil(deficit / 8)` arithmetic so "spend your next 3 points on Spirit" becomes a stated move. (Note: this takes the document past Stage 5B's "eleven sections" gate — `test/context.test.ts:374` asserts the old count and must be updated, not worked around.)

- [x] **Stage 6C — Throughput, stable ids, and a structured answer** — [docs/plans/stage-06c-throughput-and-structured-answer.md](docs/plans/stage-06c-throughput-and-structured-answer.md)
  Second follow-on from the live runs. **Attack speed is attacks-per-second and additive**, not a percentage: the player record holds the baselines (1.25 attack, 1.25 cast, 0.93 run) and a weapon's `characterBaseAttackSpeed` shifts the attack rate by −0.24…+0.01 — so `1.99` on a weapon is the game's `{%.2f} Attacks per Second` display, never "199%". Only weapons carry the term (checked every other class); the char sheet's percentage is the resulting rate over the baseline with the cap on *that*, which is what the game means by "slower weapons gain less from % Attack Speed bonuses". `_Suchka` reads **177% → 182% buffed (2.27/s) with 19 points of headroom**, and **movement already 15 points past its own raised 138% cap** — the two facts both live runs said in as many words that they could not compute. **Cunning and Spirit do scale damage** and the game's attribute descriptions say which (Cunning: Physical/Pierce/Bleeding/Internal Trauma; Spirit: the magical types; Physique: none) — but the *rate* is engine-side like the armour hit weights, so §3 names the direction, refuses to invent a coefficient, and states outright that a swap moving an attribute by tens of points against a total in the hundreds must not block the move. Also: **194 components and augments got dossier ids** from the same hash as items, which retires `verify.ts`'s strip-the-parenthetical name matching and adds `name-mismatch` (a right name on a wrong id is the failure an id-only plan hides); the plan schema gained `summary`, `keyMoves`, `projected` and per-verdict `itemName`/`targetId`/`targetName`; `verdictRows` finally carries `gains`/`costs`, which is why the first table showed a `+12% Fire Resistance` move as having no benefit; and `advise --json` writes one envelope for Stage 7. The user's "split prose and JSON into two calls" was **measured and rejected** — the JSON is 2.7k of ~30k output tokens (~$0.20 of a $3.70 run), a second call costs more on Opus and saves 4% on Sonnet, and an extractor without the dossier cannot resolve ids at all. What *was* duplicated: the model wrote a per-slot table and the CLI rendered its own, so the terminal printed it twice — the prompt now forbids the prose table and `--out` appends the rendered one. Gate: **§3 and §4 diff to 18 added lines and zero changed ones** — speed and attribute scaling are purely additive. Live run: 5 warnings → one revision → **clean**, 18 verdicts with 18/18 `itemName`, 16/18 `targetId`, 3 `keyMoves` (2 calls · $4.16 · 845s). Where Stage 6 wrote *"the dossier gives no attack-speed total, so I cannot say whether you were at the 200% engine cap"*, this run wrote *"177% → 172% permanent, 177% with buffs, headroom widens from 19 to 28 modifier points — a real ~2.8% throughput cost"*.

## Post-v1 backlog (not planned in detail yet)

- ~~Own `.arz` parser backend~~ / ~~`.arc` reader~~ / ~~drop the last download~~ — **all done**, across Stages 3–4 and the follow-on after Stage 4. The tool now reads only the installed game and makes **no network requests at all**.
- **Grammatical agreement in gendered locales.** The text files encode declension: a noun opens with the gender it *is* (`[ms]`, `[fs]`, `[ns]`, `[np]`), an adjective spells out every form it *could take* (`[ms]искусный[fs]искусная[ns]искусное[np]искусные`), and the engine matches them. `cleanText` currently keeps the first form, so Russian reads "искусный печатка" where the game says "искусная печатка". Doing it properly means carrying the base item's gender on `DbItem` and picking the affix variant in `resolve.ts` — ~25 lines, affects 365 adjectival tags, and nothing at all in English.
- **Mod support.** With text and icons both coming from `.arc`/`.arz` files, a mod's `mods/<name>/database/*.arz` + `resources/*.arc` would slot into the same merge (the save files already record which mod they belong to). Untried; the Crucible (`survivalmode`) is the only mod installed here.
- **Ascendant Altar: ascension advice (gdx3).** Awakening is deterministic and *is* wired into stages 5A/5B (recipes carry reagents; "awakened version exists" is a HOLD signal). Ascension is not: `ItemAscensionFormula` rolls a random ascended affix from per-slot tables (`affixWeight`/`masteryWeight` 600/400) for five material types + 250k iron, with reroll formulas on top — advice richer than "it exists and is a gamble" (e.g. EV reasoning over the slot's affix table, themed swap lists in `ascensionaffixswaplists/`) is deliberately deferred.
- **Aggregate fidelity round 2:** count item-granted skills (`itemSkillName` actives/procs) and item skill modifiers (`modifierSkillName<N>`) in the aggregates — Stage 5A names both but sums neither. Also: model `Skill_Transmuter` as the skill-rewriting mechanic it is rather than banding it like a modifier, and extend the damage profile / armour / non-damage-resistance figures past permanent sources. (+skills rank boosts were promoted into Stage 5A scope during the 2026-08 plan review, and effective ranks are computed there.)
- ~~Conversion-aware damage ranking~~ — **done** (Stage 5A.5): global conversion and armor piercing fold into the flats, skill-scoped conversion is typed per skill. The true remainder: a full per-skill DPS model (folding `% weapon damage` inheritance, attack speed and crit into one number per skill) stays a non-goal — the profile answers *fit*, not DPS. (The speed half of that is now **done** in Stage 6C: `aggregate.speed` resolves attack/cast/movement against the caps.)
- **The attribute → damage coefficient.** Stage 6C established *which* types Cunning and Spirit scale, from the game's own attribute descriptions, and that the **rate is in no record** — so §3 states the direction and refuses a number. Recovering the rate would mean measuring it in game (vary one attribute, read the char sheet's `+% damage` line) and pinning it the way the armour hit weights are. Worth doing only if an advice run is ever seen to turn on it; today the rule "a shift of tens against a total in the hundreds is not a damage argument" covers every real case.
- OpenAI provider behind `AdvisorProvider` (settings toggle) — registered as a stub since Stage 6; `available()` is false and `advise()` explains itself.
- **Measure `xhigh` against `high` on the same dossier.** Stage 6 deferred it: at ~8 minutes and ~$1.50 a run the experiment currently costs more than it informs, and `high` showed no reasoning gap. Worth doing once the answers have a baseline to diff against.
- **`transmutes.gst` (block 19, 36 KB)** — illusionist/transmuted appearances. Envelope verified alongside `reagents.gst` in Stage 6B's investigation; deliberately out of scope there because appearance is cosmetic and changes no advice.
- electron-builder packaging (dev-mode `npm run dev` is fine until then).
- Nice-to-haves: per-slot "shopping list" view, multi-character comparison, hardcore (`.gsh`) stash support if ever needed.
