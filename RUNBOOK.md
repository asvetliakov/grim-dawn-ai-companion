# Runbook — Grim Dawn Companion Tool

Master plan for building the tool in independent, verifiable stages. Each stage is sized for one focused Claude Code session.

## How to kick off a stage

In a fresh Claude Code session, say:

> Read RUNBOOK.md and implement stage N per its plan in docs/plans/. Verify against the acceptance criteria before finishing.

Each stage plan is self-contained (goal, format facts, deliverables, acceptance criteria, verification commands). After a stage passes verification: tick its box below, commit, and note deviations in an "Outcome" section at the bottom of the stage plan.

  Backend pivoted mid-stage: GrimTools publishes no DBR record paths, so item data comes from the game's own `.arz` archives; GrimTools supplies localization only. See the plan's Outcome.
- [x] **Stage 4 — Icon service** — [docs/plans/stage-04-icons.md](docs/plans/stage-04-icons.md)
  Per-item PNGs, cached; CLI `icon`. Gate: 0 missing icons for equipped gear — **actual: 148/148 for everything both characters can reach**, 3,840/3,844 across the whole database.
  Backend pivoted again, as Stage 3 predicted: icons come from the game's own `resources/Items.arc`, not the GrimTools sprite sheet, so the plan's `.png`-path/CSS scheme was moot. No network, and no `sharp` — see the plan's Outcome.
  Follow-on (same session): the `.arc` reader was pointed at `Text_<LOCALE>.arc`, which **removed the last download**. The tool is now fully offline, with 20,322 name tags instead of 16,246 and all 13 shipped languages instead of one.
- [x] **Stage 5A — Game mechanics layer** — [docs/plans/stage-05a-mechanics.md](docs/plans/stage-05a-mechanics.md)
  DB learns skills/devotion/sets/affix-stats; per-character resistance matrix + build damage profile; CLI `aggregates`. Split out of Stage 5 after the 2026-08 plan review: holistic advice (augment slots as free variables, damage-vs-resist trade-offs, buff-aware totals) is impossible from item base stats alone.
  Gate: Elemental Awakening bands as maintainable at **effective rank 12** (11 invested + the relic's +1 to all Nightblade skills); the profile ranks **pierce then bleeding**. Four plan facts were wrong and the data won — most importantly **the difficulty penalty is in the game files and is not uniform** (Ultimate: −50 elemental/pierce/acid, −25 aether/chaos/vitality/bleeding, **0 physical**), read from `balancingadjustment_mp+difficulty_players01.dbr` rather than hardcoded; and **armour is localized, not pooled** — six body parts with hit weights, absorption multiplicative on a 70% base. See the plan's Outcome.
- [x] **Stage 5A.2 — Item requirements & character attributes** — [docs/plans/stage-05a2-requirements.md](docs/plans/stage-05a2-requirements.md)
  Attribute requirements are **equation-derived, not stored**: `itemCostName` → `records/game/itemcostformulas*.dbr`, evaluated at `itemLevel` per slot class (spears ride `melee2h`; medals require nothing); level gates are explicit and affix-inclusive (`max(base, prefix, suffix)`); `-% Requirement` reductions are a scope × attribute matrix. Aggregate gains attribute totals (save base + mastery bars + gear ± %), OA/DA contributions, and `checkRequirements`.
  Gate: **every equipped item on both characters passes the check** — and the first run failed it, catching a real bug (jewelry's `totalAttCount` stat count inflated by non-stat keys). See the plan's Outcome.
- [x] **Stage 5A.3 — Socketable use-on slots & extraction rules** — [docs/plans/stage-05a3-socketable-slots.md](docs/plans/stage-05a3-socketable-slots.md)
  Components/augments carry a 23-flag use-on restriction, now typed as `DbItem.allowedSlots` (schema 7, 490 socketables); the Inventor's salvage verified either/or destructive from the game's own `tagDividing*` strings (extract a component → the host item dies; keep the item → the component dies; augments never survive). 5B gains a component census (single-instance marks), stage 6 a sourcing procedure + `componentFrom` and two mechanical checks.
- [x] **Stage 5A.4 — Wielding modes, set duplicates, engine caps** — [docs/plans/stage-05a4-wielding-and-caps.md](docs/plans/stage-05a4-wielding-and-caps.md)
  Gap audit follow-up: wielding mode + named dual-wield enablers (`dualWieldOnly`/`dualRangedOnly` flags; invested passives and item-granted skills enable, WPS/transmuters only require — the first live run caught the difference), DW-conditional skill stats inert outside their mode, set counters deduped to distinct members (in-game verified), `GameDb.speedCaps()` (attack/cast 200, run 135 from `gameengine.dbr`), conversion blindness of the damage ranking disclosed. 5B/6 plans gained speed-cap, soulbound, respec-economy and enabler-preservation rules.
- [x] **Stage 5A.5 — Damage-type path** — [docs/plans/stage-05a5-damage-path.md](docs/plans/stage-05a5-damage-path.md)
  Conversion-aware profile: typed conversion pairs (`Elemental` expansion, DoT twins, once-only, proportional past 100%) applied to the flat pools; `% Armor Piercing` modelled (the base weapon record's own ratio, physical only — `_Suchka`'s "+138 physical" was pierce all along); flats are min–max midpoints; `damage.weaponAttack` composition + named main attack (`Skill_WeaponPool_*`); `damage.skillDamage` types every invested attack skill (own flats, `% weapon damage`, skill-scoped conversions with transmuter nodes merged in). 5B/6 plans gained the conversion rule-book, candidate damage-identity lines and off-type trade-off rules.
- [x] **Stage 5B — Context document builder** — [docs/plans/stage-05-context-builder.md](docs/plans/stage-05-context-builder.md)
  Character + DB + aggregates (incl. 5A.2 requirements/attributes) → markdown context doc for the LLM, self-contained incl. game rules; CLI `context`. Candidates carry requirement annotations (`meets` / `short 42 physique` / `needs level 84 (HOLD)`); §8 is a component census across all containers so single-instance installed components are visible.
  Gate: eleven sections at **~36k tokens, nothing trimmed**, matrix identical to `aggregates`, **zero** raw `key: value` fallbacks anywhere in the document. §9 forced a real fix — **the save's faction slot order was guessed and wrong**; it is not in the game data, so it was derived from the live saves (fixed factions at 0–7, `factionUser<N>` at slot **N + 6**) and confirmed five ways, including the Kymon's-Chosen / Death's-Vigil contradiction Stage 1 had flagged. Also: schema 9 keeps `racialBonusRace` and `petBonusName`; skill references follow the activator→buff hop that `db.skillName` alone cannot. The plan's 30k budget turned out to be a *floor*, not a ceiling — the whole reachable candidate set costs ~36k, so the default is now 100k and the gate is a safety net for oversized stashes rather than a target. See the plan's Outcome.
- [x] **Stage 6 — AI provider + advise** — [docs/plans/stage-06-ai-advise.md](docs/plans/stage-06-ai-advise.md)
  Provider abstraction (`claude-cli` default, `mock` for tests, `openai` a registered stub); CLI `advise`. Requirement handling is a hard constraint on the post-swap loadout: enabler combos, HOLD-until-level/attribute, SELL only when build-unreachable. The four hallucination/legality checks run in `src/core/ai/verify.ts` against **what the document offered**, not the whole database.
  Gate: two live runs on `_Suchka`, both clean on every mechanical check — 139-id set, 15 socket verdicts legal, no extraction host reused, every EQUIP target annotated *meets*. `execa` was dropped for `node:child_process` (the zero-dependency rule wins; the injectable `spawn` is what makes every error path testable). **The 180s timeout was wrong by 3×** — a real run is **496s** at ~36k in / ~40k out, so the default is now a 900s runaway ceiling, and the first live attempt died at 300s proving it. See the plan's Outcome for what the advice actually reasoned about.
- [ ] **Stage 6B — Unread containers, component semantics, advice legibility** — [docs/plans/stage-06b-advisor-feedback.md](docs/plans/stage-06b-advisor-feedback.md)
  Follow-on from the user's review of the first live `advise` runs. **`reagents.gst` (block 20) — the shared crafting-material and component store — has never been opened**, which is why every loose component reads `[inv]` and the materials line says "Royal Jelly ×6"; the envelope is verified and four hypotheses are already ruled out in the plan, so the next session starts from a lead, not from scratch. Plus: loose components print no stats, `Grants: <skill>` never follows the buff hop, the per-copy buff stacking rule is unstated, §10 narrows to components + relics, the on/off-type note names its evidence instead of reading as a verdict, every stat reference gets `Resistance`/`Damage` (a mechanical `ambiguous-stat` check, since `+99% Pierce` and `+22 FCL` meant different things four words apart), the CLI renders its own `Slot | Current | New | Action` table from the structured plan, and `checkPlan`'s warnings get fed back for exactly one revision. Two more from the same review: **a dual-wield enabler from an invested mastery passive is permanent and survives every gear change** — the dossier names all three of `_Suchka`'s but flattens them into one list, and the advice duly kept a relic "for the Bloodbath enabler" that two learned passives already made redundant; and iron budgeting becomes conditional on a computed verdict rather than always-on, since 35,500 against 1,315,676 is noise (it stays loud for a genuinely poor character). Finally a **twelfth section, the "unlock ladder"**: the HOLD data already knows that nine of `_Suchka`'s twelve held items unlock at level 84 and that three attribute points into Spirit buy one more, but it reads as twelve unordered rows — §12 groups by shared threshold and does the `ceil(deficit / 8)` arithmetic so "spend your next 3 points on Spirit" becomes a stated move. ## Post-v1 backlog (not planned in detail yet)

- ~~Own `.arz` parser backend~~ / ~~`.arc` reader~~ / ~~drop the last download~~ — **all done**, across Stages 3–4 and the follow-on after Stage 4. The tool now reads only the installed game and makes **no network requests at all**.
- **Grammatical agreement in gendered locales.** The text files encode declension: a noun opens with the gender it *is* (`[ms]`, `[fs]`, `[ns]`, `[np]`), an adjective spells out every form it *could take* (`[ms]искусный[fs]искусная[ns]искусное[np]искусные`), and the engine matches them. `cleanText` currently keeps the first form, so Russian reads "искусный печатка" where the game says "искусная печатка". Doing it properly means carrying the base item's gender on `DbItem` and picking the affix variant in `resolve.ts` — ~25 lines, affects 365 adjectival tags, and nothing at all in English.
- **Mod support.** With text and icons both coming from `.arc`/`.arz` files, a mod's `mods/<name>/database/*.arz` + `resources/*.arc` would slot into the same merge (the save files already record which mod they belong to). Untried; the Crucible (`survivalmode`) is the only mod installed here.
- **Ascendant Altar: ascension advice (gdx3).** Awakening is deterministic and *is* wired into stages 5A/5B (recipes carry reagents; "awakened version exists" is a HOLD signal). Ascension is not: `ItemAscensionFormula` rolls a random ascended affix from per-slot tables (`affixWeight`/`masteryWeight` 600/400) for five material types + 250k iron, with reroll formulas on top — advice richer than "it exists and is a gamble" (e.g. EV reasoning over the slot's affix table, themed swap lists in `ascensionaffixswaplists/`) is deliberately deferred.
- **Aggregate fidelity round 2:** count item-granted skills (`itemSkillName` actives/procs) and item skill modifiers (`modifierSkillName<N>`) in the aggregates — Stage 5A names both but sums neither. Also: model `Skill_Transmuter` as the skill-rewriting mechanic it is rather than banding it like a modifier, and extend the damage profile / armour / non-damage-resistance figures past permanent sources. (+skills rank boosts were promoted into Stage 5A scope during the 2026-08 plan review, and effective ranks are computed there.)
- ~~Conversion-aware damage ranking~~ — **done** (Stage 5A.5): global conversion and armor piercing fold into the flats, skill-scoped conversion is typed per skill. The true remainder: a full per-skill DPS model (folding `% weapon damage` inheritance, attack speed and crit into one number per skill) stays a non-goal — the profile answers *fit*, not DPS. Related and still open: sum the character's actual attack/cast/move speed totals against `GameDb.speedCaps()` so "already capped" is computed rather than left to the advisor.
- OpenAI provider behind `AdvisorProvider` (settings toggle) — registered as a stub since Stage 6; `available()` is false and `advise()` explains itself.
- **Measure `xhigh` against `high` on the same dossier.** Stage 6 deferred it: at ~8 minutes and ~$1.50 a run the experiment currently costs more than it informs, and `high` showed no reasoning gap. Worth doing once the answers have a baseline to diff against.
- **Sum the character's attack/cast/move speed** against `GameDb.speedCaps()`, so "already capped" is computed rather than left to the advisor. Both live runs said plainly that they could not check it — the one gap from their self-reported limitations that Stage 6B does *not* close.
- **`transmutes.gst` (block 19, 36 KB)** — illusionist/transmuted appearances. Envelope verified alongside `reagents.gst` in Stage 6B's investigation; deliberately out of scope there because appearance is cosmetic and changes no advice.
- electron-builder packaging (dev-mode `npm run dev` is fine until then).
- Nice-to-haves: per-slot "shopping list" view, multi-character comparison, hardcore (`.gsh`) stash support if ever needed.

## Risk log

| Risk | Mitigation | Status |
|---|---|---|
| Save format drift (1.3.0.6 vs 1.2-era specs) | Checksums catch misparses immediately; unknown blocks skipped; warn-not-throw on version fields | Settled empirically by Stage 1 |
| Torn/partial save writes | Checksum + 3× retry + `player.g00` fallback | Designed in (Stage 1/7) |
| ~~GrimTools schema change or unavailability~~ | Nothing is downloaded any more — names come from the game's own `Text_<LOCALE>.arc` | **Closed** (after Stage 4) |
| Affix (prefix/suffix) name coverage | Answered: the `.arz` names every affix that has a name (`lootRandomizerName`); only crafting bonuses are nameless, and they are nameless in game too | Closed (Stage 3) |
| Requires a local Grim Dawn install | Unavoidable — record paths exist nowhere else. Auto-detected; `GD_GAME_DIR`/settings override; absence reports a plain message | Accepted (Stage 3) |
| Resistance totals are approximations | Stage 5A aggregates items + affix stats + components + augments + sets + passive/toggled/maintainable skills + devotion, banded by reliability; +skills rank boosts *are* folded in (effective ranks); remaining gaps (item-granted skills, item skill modifiers, procs/potions/pets) are *listed as exclusions* in the output rather than silently missing. Full engine simulation stays a non-goal | Narrowed (Stage 5A) |
