# Grim Dawn AI Companion

A desktop companion for Grim Dawn, developed on macOS (the game runs under CrossOver; this tool runs natively). It parses character saves, knows the game item database (incl. faction vendor augments per reputation tier), shows equipped/available gear with icons, watches the save folder so the window keeps up with the game, and on demand compiles a context document and asks an AI (Claude CLI by default) for equip/replace/hold recommendations.

**The displayed name is "Grim Dawn AI Companion"** (`APP_NAME` in `src/shared/ipc.ts`, `productName` in package.json, `app.setName` before `ready`) and the on-disk identity is `gd-ai-companion`. The npm package stays `gd-companion`: it names nothing a user sees, and Electron reads `productName` in preference to it.

## How work is organized

Implementation runs in ordered stages, one focused session each. **Start every implementation session by reading `RUNBOOK.md`**, then the stage plan it points to under `docs/plans/`. Stage plans are self-contained — trust them over re-deriving format details. When a stage is done and verified, tick its checkbox in `RUNBOOK.md` and note any deviations in the stage plan's "Outcome" section (add one if needed).

## Stack & conventions

- TypeScript ^5.9, `"type": "module"`, strict mode. Node v24 on this machine.
- All logic lives in `src/core/` — **plain Node, zero Electron imports**. The dev CLI (`src/cli/index.ts`, run via `npm run cli -- <cmd>`) and vitest exercise it. Electron (`src/main`, `src/preload`, `src/renderer`) arrived in Stage 7A and stays a thin consumer. **Main and preload are both CommonJS `.cjs`** — an ESM preload requires `sandbox: false`, and Node cannot see named exports through Electron's CJS shim, so an ESM main dies on `import { BrowserWindow }` before it runs a line. **The renderer compiles with `types: []`**, which makes "no Node import reaches the renderer" a compile error rather than a convention; the IPC DTOs therefore live in `src/shared/` and `src/core/view.ts` implements against them.
- **The save watcher is `node:fs.watch`, not chokidar** (`src/core/watcher.ts`). The stage plan called for the dependency and the zero-dependency rule won, as it did for `sharp`, `execa`, `react-markdown` and `lucide-react`: `fs.watch(dir, { recursive: true })` is FSEvents on macOS and ReadDirectoryChangesW on Windows — the two platforms this runs on — and everything chokidar adds is either unnecessary or is the debounce-and-parse loop that has to exist anyway. **The parsers do not throw on a torn write**, which is the fact the module turns on: Stage 1's "skip an unknown block, never be fatal" rule means a half-written save comes back as an ordinary `CharacterSave` with `checksumOk: false` on a block (or a truncation warning), so a watcher catching only exceptions would announce every autosave as an update. `parseProblem` is the check; on a healthy save every block verifies, including the ones we do not decode (15 of 15 live). The watcher hands the parsed save on via `SnapshotOptions.preparsed` rather than letting main re-read it — re-reading would re-run the race the retries just won, and on the backup path it would lose it.
- **Path detection is composed from three roots, not written out** (`src/core/platform.ts`): `windowsRoots()` (every `drive_c`-alike — CrossOver and Whisky bottles, a Wine prefix, Steam's Proton prefix, or real drive letters on Windows), `steamRoots()` (incl. libraries on other drives via `libraryfolders.vdf`) and `documentRoots()` (incl. OneDrive's redirected `Documents`). **Both stores are covered on every platform** — Steam under `steamapps/common`, GOG under `GOG Games` / GOG Galaxy / `Games` — because the store is orthogonal to the wrapper. Saves are Steam Cloud's `userdata/<id>/219990/remote/save` *or* `Documents/My Games/Grim Dawn/save` (GOG, and cloud-off Steam); a directory counts only if it has a `main/` in it. The native macOS `~/Documents` is deliberately excluded — nothing puts a Windows game's saves there and it is TCC-protected.
- **Zero runtime dependencies beyond `commander` + `zod`.** The `.arz`/`.arc` readers, LZ4, the DDS decoder and the PNG encoder are all hand-written against `node:zlib` and friends; Stage 4 dropped the planned `sharp` because there was nothing left for it to do (see its Outcome). No native modules means no Electron ABI rebuilds. The renderer gets icons via the `gdicon://` custom protocol, which is `createIconService().getIconPng` in the main process. **Item icons only — the game's own `UI.arc` chrome was tried in Stage 7A and dropped**: that art is cut for the engine's fixed layout, so at the app's sizes it overlaps and fights the content. Don't re-add it.
- Tests: vitest. Real save files are the fixtures (paths below); tests needing stability snapshot-copy them into git-ignored `test/fixtures/` on first run.
- **The renderer's typeface is Inter Variable** (`--font` in `styles.css`), chosen over a serif and over Montserrat because nearly every glyph on screen is a number in a narrow column: Inter has the x-height to survive 12 px, unambiguous `1/l/I` and `0/O`, and real tabular figures. **Stat lines are coloured by damage type** from the finished string (`statColors.ts`) — safe only because Stage 6C made "every stat reference names its kind" a mechanical check, so `Fire Resistance` and `Fire Damage` are both spelled out. The palette is spread around the wheel on purpose; the game crowds fire/chaos/bleeding/vitality into one warm corner. **The rule reads a stat *line*, so it applies to stat lines, sheet row labels and table cells — never to prose**: a paragraph that says "Bleeding" once is not a stat line, and colouring the sentence red makes an argument look like a warning.
- **The UI humanises the template class** (`ArmorProtective_Head` → "Head Armour", in `src/core/view.ts`). The **context document keeps printing the raw class** — its bytes are the id-stability contract, so never "tidy" it.
- **`UiSnapshot.socketables` is the dossier's socketable table by id, and `UiSocketable.id` is the same id on the installed copy.** A plan proposes components and augments by id, and a *proposed* one is installed nowhere — there is no item to read its stats off. One id (`shortHash(record)`) serves the worn copy, the loose one and the proposed one, which is the join a `SWAP-COMPONENT` needs. Four of the seven verdicts keep the item and change what it carries; only `EQUIP` replaces it, so those four render **the same item again** with the new socketable in it (`withSocketable` in `LoadoutPanel.tsx`) rather than the socketable alone.
- **`HOLD` is a recommendation, not a status** — "on the day the threshold is met you will put this on". Being unequippable is neither necessary nor sufficient: §12 lists every blocked candidate so a threshold can be costed, and reading that as a to-do list marks every over-levelled item in the stash. `hold[]` therefore carries `slot`, `beats` and `gains`, and `checkPlan` reports `unjustified-hold` without them. Don't relax this back to "cannot equip yet". Same rule one layer up: the **UI tooltip** states a level gap as `needs level 84 — 2 more` and says nothing about holding; only the *document* writes `(HOLD until then)`, because there it is telling the advisor not to reject a candidate over a deficit levelling will close.
- **The advice mark on a container item is typed, not a boolean**, and it is **four kinds in four colours**: `equip` (green, put it on now), `hold` (amber, the colour the threshold is written in), `sell` (red — the traffic-light reading, and the commonest mark by far: thirteen of sixteen on the first live run) and `destroy` (violet `--spend`, deliberately *off* the red/amber/green scale, because an extraction spending a host is not a point on a scale of urgency) — `actionMarks` in `advice.ts`. One colour for all four turns a stash of things to wait for into a stash of upgrades. The mark is a **bar along the bottom edge, plus a faint tint, plus the glyph badge** — and the shape was settled by getting it wrong twice. A **corner flag** is 11 px in a 32 px cell in a grid of two hundred and cannot be found. A **full ring** is perfectly visible and reads as *lit*: a border around a cell is how this window says "this one", so sixteen standing marks may not borrow that vocabulary, and dimming it does not help because the problem was never brightness. **A border is a state; a bar is an annotation.** Light — a glow, and the bright `--lit` border — belongs to the pointer alone.
- **Loadout and Advice share the right-hand column as tabs, and the tab follows the run.** Stacked, the advice panel sat below fourteen slot rows — off screen exactly when a run was streaming its reasoning. A run **starting** opens Advice (the transcript is what there is to watch, and the tab carries a pulsing dot readable from the other side); the run **finishing** goes back to Loadout, because the result of a run is marks and proposals on the gear, not the table about them. The switch-back yields to the reader — a manual tab change during the run pins the column until the next run starts — and a **failed** run stays on Advice, where the error sentence is; a *refused* start (which never becomes a run) surfaces Advice via its own effect. Opening a *stored* run switches nothing: only a run moves the column. The strip is `.column-tabs` (sticky over the pane, like the container chrome) because bare `.tab` also matches the container tabs.
- **Two IPC-timing rules the run controls depend on.** Electron does not order an `invoke` reply against `send` pushes, so `startAdvice`'s optimistic "it started" state can arrive *after* the run's `advise-done` — `endedRuns` in `session.tsx` keeps a finished runId from being resurrected into a phantom run. And when the answer lands while the renderer is busy, every push can collapse into one React render: the run is over before it was ever on screen, so run-transition effects (like the tab switch-back) legitimately never fire. Only the mock is fast enough to hit either; `check-app.mjs` tolerates the second explicitly rather than pretending it cannot happen.
- **The container legend is the control for its own count.** Hovering "sell or salvage 13" lights those thirteen cells. Scoped to the containers by being a *kind* (`litKind` in `highlight.tsx`) rather than a set of ids: the legend counts what is in the containers, and an id-based highlight cannot tell a candidate in a stash from the loadout proposal naming it, because they are the same item.
- **A verdict can carry socketables its verdict word cannot name** (`fits` on `verdictSchema`). One verdict per slot has one name, and an item holds a component **and** an augment in independent sockets — so an `EQUIP` that should also be fitted with a component, or a `RE-AUGMENT` beside a free component fill, had nowhere to put the second instruction. The first live run hit it twice and said so in `projected.notes`: *"two free component fills are part of this plan and are not separate verdict rows"*. `target`/`targetId` stay the socketable the verdict is *named* for; `fits` is everything else. A fit's legality is checked against the item the slot **ends up** holding — the candidate for an `EQUIP` — because checking the outgoing item would clear a component for gear the plan is telling you to take off.
- **The stored envelope records the loadout it was written against** — `worn` (slot label → item id) **and `wornSockets`** (slot label → the component/augment ids it carried). The second field is not optional in practice: **an item's document id includes its attachments** (`itemId` hashes `relicName`/`relicSeed` — the save's word for a component — and `augmentName`/`augmentSeed`), so carrying out an `ADD-COMPONENT` changes the worn item's id without changing the item, and `worn` alone reports that as *"Feet now holds Bloodhound Greaves (was Bloodhound Greaves)"* — useless, and the opposite of the truth. `loadoutDrift` therefore classifies each moved slot as an item change or a socket change, and a socket move counts as **done** when the socketable now installed is the one the plan named (verdict target or `fits`). The notices live at the **top of the Loadout pane** and each affected slot carries a bordered `DONE`/`CHANGED` stamp with a glyph, because both are statements about those fourteen rows.
- **The stored envelope's loadout record splits the comparison in two.** **Acting on the advice is what makes the loadout differ from it**, so a single "is it stale" bit calls an answer stale as its reward for being followed — and discarding the stored run on a mismatch, which is the design that suggests itself next, deletes a twelve-minute answer at the moment the user does what it says. `loadoutDrift` therefore reports `applied` (the slot now holds what the plan named — green, and the row struck through) separately from moved (amber, named so the reader knows which verdicts to ignore). Never collapse them, and never drop the run.
- **Advice runs are kept, not overwritten, and nothing in the window deletes one** — `advice/<character>/<timestamp>.json`, newest first, reached through the run picker. Each run is minutes and real money, so taking a second opinion must not be a decision to destroy the first answer. The store validates every file on read and skips what it does not recognise, and it migrates the pre-history flat `advice/<character>.json` on first read.
- **The window opens on the empty state, and the picker is the door.** It used to reopen the newest answer on launch, which put a stale plan's marks on the gear before the reader asked for them and made *"is this still about what I am wearing?"* the first question of every session. So there is **no `getLastAdvice` channel** — `getAdviceHistory` → `getAdvice` is the whole path in — and the empty state says how many answers are kept, because starting fresh must not read as having lost them. A **re-read never changes which run is open**: `load()` runs on every window focus (and will run on Stage 7C's watcher), so opening or closing a plan there would take the marks off the gear at the exact moment the user came back from the game to compare them. A *different character* is the one case where the selection is dropped. The picker itself lives **in the header and only there** (the panel copy was sometimes off screen and always a duplicate; the panel shows the open run's date), it is rendered **whenever any run exists** — hiding it "when there is nothing to choose" once left a single open run with no way back to the empty state short of restarting the app — and its first entry is **`New run`**, the fresh session as a real option rather than a "N saved answers" placeholder.
- **One run control at a time, and `New run` is not a delete.** With an answer on screen there is **no Re-run** — a second opinion costs eight minutes and a few dollars and does *not* replace the answer beside it, so a Re-run button next to a finished plan is an expensive misclick waiting to happen. Asking again is two steps on purpose: `New run` puts the answer away (it stays in the picker) and the Run button comes back with the question box. The picker's own `New run` entry is the same action by another road, not a second behaviour. This replaced a `Clear` that **deleted** the run it sat beside, which is worth remembering as a mistake: it put a four-dollar answer one click from gone under the very button a reader reaches for *after acting on the plan* — "I have done these, ask me again". There is consequently **no `deleteAdvice` channel** either, and `--bad` red is off that button.
- **A control's tooltip is written for the person using it, not the person who built it.** `Refresh` says it reads your save file again and picks up what you are wearing; it does not mention the item database, the dossier, the snapshot or the envelope. `check-stories.mjs` asserts that vocabulary is absent, because the drift back into it is not a hypothetical — every one of those words was in these three tooltips.
- **Every control in a toolbar row is one height** (30 px, `box-sizing: border-box` — `styles.css`). The row mixes a 15 px select, a 14 px button and a 12 px picker, so left to their contents they are three heights on one baseline, which reads as a row that has not been laid out. The picker is **narrower inside the advice panel** than in the header (230 vs 340): the panel is ~690 px, and at 340 the picker pushed `New run` onto a second line to show 100 px of a label whose full text is in the open list anyway.
- **The advice prose is shown without the plan block that ends it** (`answerProse` in `src/shared/answer.ts`). Every field in that block is already on the Plan tab as something hoverable; as raw JSON it was 17k of the first live answer's 28k. The rule is "strip the block the Plan tab is rendering", decided by **parsing** the body rather than by its info string — `parseAdvice` accepts a bare fence, so going by the tag alone eats any code block an answer happens to end on. Stripped on the way out only: the envelope keeps the model's exact words, because the plan is re-parsed from them.
- **`claude` is invoked with `--output-format stream-json --include-partial-messages --verbose`, and the last line is the same envelope `json` printed on its own.** So this is a change to the invocation, not to the parsing (`envelopeFrom` reads both). It exists because the phase label says "asking the model" for ten minutes either way and cannot distinguish a working run from a wedged one; the stream carries `thinking_delta`/`text_delta` and the CLI's own `thinking_tokens` estimate. The runner **coalesces** to ~4 pushes a second and pushes **deltas**, which the renderer accumulates into the whole transcript — a snapshot per push would re-marshal a hundred kilobytes several times a second to append a few words. **The transcript is the reasoning and only the reasoning.** The first live run streamed the answer through it too, and that buried the box twice over: thirty thousand tokens of markdown shoved the reasoning off the top, and the repair call re-streamed a whole second answer under it — two copies of a document the panel was about to render properly anyway. So answer deltas travel with empty text and only move the token count, the repair transition drops a `— revising the plan —` seam into the box, and the panel shows the reasoning **whole**, expanded while the run is live and collapsed to one line after: *"why did it decide that"* is a question the finished answer routinely raises and does not answer. The box's height is **capped and scrolls**, since one that sized itself to its contents would reflow the panel for twelve minutes; the scroll is pinned to the bottom only while the run is live *and* the reader has not scrolled away. `AdviseStatus` still carries a bounded **tail** (reasoning only, like the box), for the other case — a window that mounts nine minutes in has no transcript to append to, and says so rather than presenting a fragment as the whole. The transcript is **not persisted** with the envelope: it is the working-out, not the answer. Written tokens, never a percentage. **As of CLI 2.1.220 the reasoning *text* arrives redacted** — every `thinking_delta` carries an empty string (verified with a live probe); what survives is the `system:thinking_tokens` estimates and the final `message_delta`'s count. The reader therefore emits those estimates as empty-text thinking activity so the token count still ticks through the thinking phase (previously nothing at all was pushed until the answer began), and the box says the model keeps its reasoning to itself rather than sitting blank; a finished run with an empty transcript doesn't keep the box at all. The transcript machinery stays — the mock streams text, and a CLI change could bring the prose back.
- **The hover panel is centred on its subject, not left-aligned with it.** With two panels for a marked item, left-alignment meant the pair extended right until it hit the viewport and `shift` slid the whole thing left — so an item's own panel sat somewhere different depending on whether the plan had anything to say about it, and jumped as the pointer crossed from a marked cell to an unmarked one. Centred, the pair grows symmetrically. The *seam* between the two is not centred and should not be: that would put the panel describing the item entirely to one side of it.
- **The expensive and destructive buttons explain themselves in the window's own panel, and carry no `title`** (`ExplainedButton` + the `note` tooltip subject). A run is eight minutes and a few dollars, `Clear` deletes one, and "does Refresh interrupt a run?" is asked once by everybody — that is a paragraph, not a label. Native `title` took about a second to appear, rendered in the OS's style and vanished while being read; keeping both meant the OS box landing on top of the panel a second later, and there is no way to suppress one without the other.
- **A damage-over-time type gets its own shade of its parent's colour.** The six twins are named `Burn`, `Frostburn`, `Electrocute`, `Poison`, `Vitality Decay`, `Internal Trauma` (the game's own `tagCharStats*` strings). They convert together, but they cap and resist separately, so they are the same hue one shade lighter — not the same colour. Bleeding has no twin and never converts, so it is not one of them. `Poison` and `Acid` are separate *damage* types with a shared resistance: `Acid Resistance` reads as acid, `Poison Damage` as poison.
- **Tooltip hover targets listen on `mouseover`, not `mouseenter`.** `mouseover` bubbles from whichever child is under the pointer, so icon → component chip → name re-asserts the right subject at every step; `mouseenter` fires once on the way in and never again. The chip has no leave handler — leaving it for the name is a `mouseover` on the face, and a `hide` would race that. `TooltipProvider` returns the previous subject unchanged when nothing changed, so the extra events cost no re-renders. **The panel is a hover target itself**: it takes pointer events (`pointer-events: auto`) and closes 140 ms *after* the pointer leaves, so a reader can move into it to read a long block or select a line — an immediate close would fire in the 8 px `offset` gap and the panel would vanish on the way. Every `show` cancels the pending close, and so does the panel's own `mouseenter`. Consequence for `check-stories.mjs`: never hover a new target while a panel is up — `.hover()` retries by *moving the mouse onto the covering panel*, which keeps it alive forever. `clearTip()` parks the pointer and waits for `.tooltip` to detach.
- **The window is sized against the *work area*, not the screen** (`src/main/window-size.ts`): a 1920×1080 monitor has already spent rows on the menu bar and Dock, and a window asked for 1080 opens with its footer underneath the Dock. Where it *was* is remembered in a sibling **`window.json`**, not in settings.json — that file is choices a user made and may hand-edit, this is state written on every drag — and `restoreBounds` clamps the size and **re-centres** a window whose monitor has gone, rather than restoring it invisibly off-screen. `alwaysOnTop` is the other way round: it is a choice, so it lives in settings.json and the menu checkbox, the settings pane and a hand-edited file all take the same road.
- **Settings and the context document are the window's two covering panes**, both `Modal`, reachable from the header, the menu bar (⌘, and ⌘D) and — for the document — a button in the settings pane. The old read-only `Paths` popover is gone: it *showed* the save and game directories and gave no way to change either, so "it is reading the wrong install" had no answer but hand-editing JSON. **A path is typed or picked, never only guessed** — detection offers what it found and the text field always takes an arbitrary path, committing on blur rather than per keystroke because `gameDir` and `locale` each drop the item database. The **backend and model are dependent selects**, not text: `opus` means something to the Claude CLI and nothing to another backend, and a model typed for the wrong one fails eight minutes into a run instead of at the moment it was typed. The context viewer opens **rendered** and keeps a **Raw** tab, because the document's exact bytes are the id-stability contract — a viewer that could only show a rendering would be showing something the model never received.
- **A save the watcher cannot read is a warning, not an error.** The last good snapshot is still on screen and still true — it is simply not the newest one — so `save-problem` paints the amber banner and leaves everything up, where `error` means the window has nothing to show.
- **The game ships no damage-type palette, and neither does the Rainbow Filter.** Checked: `Text_*.arc` marks every damage type with the same generic `{^S}` code, and the only colour-named `.arz` records are UI pulse animations. The Rainbow Filter ([WanezGD_Tools](https://github.com/WareBare/WanezGD_Tools), MIT) emits those same `^` letter codes — the letter → RGB table is in the engine binary, not in any shipped file. The `--type-*` palette is ours, picked for contrast on this ground. Don't go looking again.
- **The window's two side columns are measurements, not fractions** (`styles.css`): the sheet is 540 px because the resistance table is 506 wide with the projection column, the containers 625 px because a stash tab is 19 cells of 32 px — a column narrower than its widest container scrolls sideways forever. The loadout takes the remainder; it is the one pane whose overflow (a long item name) has an answer, namely ellipsis plus tooltip. Don't convert these back to `fr`.
- **The floating layer holds two panels and takes no pointer events itself.** Since Stage 7B a marked item shows what it *is* beside what the plan says to do about it, and the two are different heights — so the flex row's own box is taller than the shorter panel, and an `auto` there puts an invisible hover target in the empty ground beside it (the pointer sits in open space and the tooltip refuses to close). `pointer-events: none` on `.tooltip-layer`, `auto` on each `.tooltip`, and `gap: 0` — a gap belongs to neither panel, and crossing it hands the pointer to the item cell underneath. Consequence for `check-stories.mjs`: `.tooltip` matches two elements, so anything meaning "the item's stats" must say `.tooltip:not(.action-tooltip)`.
- **A panel whose subject leaves the document closes itself.** `hide` rides the anchor's `mouseleave`, and an unmounted anchor fires no events — so a hovered control that unmounts (a run finishing swaps the button under a stationary pointer; a tab switch takes the whole panel) orphaned the tooltip at the viewport's top-left over the column tabs, swallowing clicks. The open timer refuses a disconnected anchor, and a 250 ms poll closes an open panel whose anchor has gone. This shipped and cost an evening: the symptom was an app-check click "intercepted by `.control-note`" at (0,0).
- **A panel waits 200 ms to appear and 220 ms to go, and the wait applies to every change.** Delaying only the *cold* open and switching instantly afterwards was tried and reverted: it made the two cases feel like different controls, and brushing a component chip on the way to the panel still flashed the component and flashed back. The anchor moves **with** the subject, not with the pointer, or the panel slides to the new card while still describing the old one. `showTip()` in `check-stories.mjs` exists because waiting for the panel to *attach* is not enough on a switch, where a panel is already up and only its contents change.
- **The panel takes the wheel, so it has to hand it on.** It is portaled to the body, so a wheel over it reaches neither the panel (usually nothing to scroll) nor the pane it covers (not an ancestor). A panel taller than the viewport scrolls itself; one with nothing left to scroll forwards the delta to the pane the *card* lives in. A **mouse notch is eased** over frames because Chromium animates one and a delta applied in a single frame reads as clunky beside the container next to it; a **trackpad gesture is passed straight through**, because easing a stream of small deltas puts the scroll four frames behind the fingers. The listener is native (React registers `wheel` passively at the root) and attached from the **ref callback**, since `FloatingPortal` mounts its child in an effect and an effect here finds the ref still null with nothing left to change.
- **The highlight follows the panel's subject, not the pointer** — a second *held* set unioned with the pointer's (`holdHighlight`), because moving onto the panel to finish reading it emptied the pointer set and took the card and its container copy dark mid-sentence. Everything else that highlights (a verdict row naming two items, a key move naming four) really is transient, which is why this is a second set rather than a sticky first one. A **socket-move row renders the same item twice** — the proposal is the host with a new socketable in it and carries the same `docId` — so the row remembers which side was pointed at and filters by it *only* where the two ids collide; filtering an EQUIP that way would stop a verdict row from lighting the worn item.
- **`envelope.ts` is in the renderer's type graph; the advice *file* is not.** `src/shared/ipc.ts` names `AdviseEnvelope`, and the renderer compiles with `types: []`, so a `node:fs` import in `envelope.ts` is a compile error — which is the guarantee, not an inconvenience. Persistence lives next door in `advice-store.ts`, and `buildEnvelope` describes its `AdviseRun` argument structurally rather than importing `RepairOutcome`, which would drag `verify.ts` → the resolver → the database types across the same boundary. A stored envelope is **validated** on read and degrades to `undefined`: an old cache file must never stop the app starting.
- **The advisor's `answer` markdown is parsed to a tree, never to HTML** (`markdown.ts` + `Markdown.tsx`, hand-written because the repo takes no runtime deps). Every leaf is text and React puts text in a text node, so an answer cannot inject markup into the window — true by construction rather than by escaping. Keep it that way.
- **The seam between the window and the core is checked by driving the real app** (`npm run app:check`, `scripts/check-app.mjs`, Playwright's `_electron`). Storybook covers the renderer and vitest covers `src/core`; neither can reach the preload bridge, the IPC channels, the run manager or the advice file. It runs against the **mock** advisor in a throwaway `GD_DATA_DIR`, so it costs nothing — point `GD_DATA_DIR` at a real settings file for a live run.
- **UI work is reviewed in Storybook, not Electron.** `npm run storybook`, then `npm run stories:shoot` (Playwright screenshots at 1920×1080) and `npm run stories:check` (interaction assertions). Stories run against `src/renderer/src/fixtures.ts`, whose every name and stat is **invented** — a fixture cut from a live save is game-derived data and cannot be committed, and synthetic data keeps the screenshots deterministic. `icons.tsx` is the seam: the app resolves art through `gdiconUrl`, the stories through a generated SVG swatch.
- Key swap seams — keep these interfaces clean: `GameDb` (`src/core/db/types.ts`; backed entirely by the installed game — `.arz` records, `.arc` text and icons) and `AdvisorProvider` (`src/core/ai/provider.ts`; claude-cli and codex-cli, both real).
- **The tool makes no network requests.** Everything comes from the install; `src/` contains no `fetch`. Advice calls (Stage 6) shell out to the `claude` or `codex` CLI, which is the one exception and goes through `AdvisorProvider`. Don't reintroduce a data download — a published dump lags the installed build, which is the mistake stages 3 and 4 each had to undo.

## Machine-specific paths

- Game install (v1.3.0.6, all 3 expansions) — **required**, it is the item database:

## Domain gotchas (hard-won; do not re-litigate)

- Save files use a seeded XOR stream cipher; **every block ends with a checksum that must equal the running cipher state**. A passing checksum is proof the parser consumed the block correctly — treat checksum assertions as the primary test. Unknown block IDs must be skipped (cipher state still advanced), never fatal.
- The cipher state advances over **ciphertext** bytes, not plaintext. Block lengths are read XOR-state **without** advancing.
- `transfer.gst` item X/Y coordinates are **floats**; `player.gdc` inventory/stash X/Y are **i32**. This is the classic porting bug.
- **`reagents.gst` / `potions.gst` are `transfer.gst`'s format with the entries wrapped in nested blocks.** Magic `1` (not `2`); the store's identity is its block id (19 transmutes, 20 reagents, 21 potions). Body: `version u32`, the same non-advancing quirk word the stash carries, `mod` string, `count`, then `count ×` a nested block (id **0**, exactly like a stash sack) holding `record string` + — in `reagents.gst` only — `quantity u32`. Two non-advancing reads per entry (the nested length and its checksum) is the entire reason a uniform "every byte advances" walk desynchronizes progressively. `potions.gst` entries stop after the record path, and the nested block's own length is what says so. **The store keeps rows at quantity 0** — a "has held this before" marker, not stock; `resolveCharacter` drops them, because every consumer floors `stackCount` at 1 (a save's own count is 0 for non-stackables) and a zero would otherwise read as one on hand. `transmutes.gst` is cosmetic and stays unparsed. **This store is where loose components actually live** — a bag copy is the exception.
- **Levelling rates are in the game data, not folklore.** `records/creatures/pc/playerlevels.dbr`: `characterModifierPoints = 1` (attribute points per level), `strengthIncrement`/`dexterityIncrement`/`intelligenceIncrement = 8` (attribute per point — strength=Physique, dexterity=Cunning, intelligence=Spirit), `maxPlayerLevel = 100`, `maxDevotionPoints = 55`. Read via `GameDb.levelProgression()`; never hardcode the 8. Levels and points stay in their own currencies in any user-facing text — a level costs XP as well as a point.
- Faction reputation: array index = faction identity (no names in the save); tier thresholds Friendly ≥1501, Respected ≥5001, Honored ≥10001, Revered ≥25000. "Trusted" is a rep level but NOT a vendor market tier. **The slot order is not in the game data** — `gamefactions.dbr` holds the roster as a *set* of keys and the `.arz` sorts fields alphabetically — so it was derived from the live saves and is pinned in `src/core/save/factions.ts`: the eight non-`User` factions fill slots 0–7 (player, survivors, aetherials, cthonians, outlaws, beasts, drifters, neutralnpc) and **`factionUser<N>` sits at slot N + 6**. Don't re-guess it; the previous guessed table put Kymon's Chosen and Order of Death's Vigil at Honored together, which the game makes impossible.
- Items in saves are DBR record paths + a seed — all display names/stats/icons come from the game DB, resolved via `src/core/resolve.ts`.
- **Icons come from the game, not GrimTools.** `DbItem.iconPath` is the DBR `bitmap` field — an in-archive `.tex` path (`items/enchants/enchantm_black.tex`). Its first segment names the `.arc` (`resources/Items.arc`), the rest is the entry; search gdx3 → gdx2 → gdx1 → base, same last-wins order as the `.arz` merge. A `.tex` is a 12-byte `TEX\x02` wrapper around a DDS whose magic reads `DDSR`; item icons are always uncompressed **BGRA** (never DXT), masks are all zero, rows top-down. Do not re-add the GrimTools sprite sheet / `itemdb.css` — it is keyed on a many-to-one `bitmap` filename and shows the wrong art where records reuse it. See stage 4's Outcome.
- **GrimTools publishes no DBR record paths** (verified: zero `records/` strings in `itemdb.js`; its `bitmap` field is many-to-one because records reuse art). Item identity therefore comes from the game's own `database/*.arz` archives, merged base → gdx1 → gdx2 → gdx3 last-wins. Do not re-add `itemdb.js`; it is 8.7 MB and carries nothing we need. See stage 3's Outcome.
- **Names come from `resources/Text_<LOCALE>.arc`** — plain `key=value` files, UTF-8, CRLF, `#` comments, BOM on the base archive's first file; merged in the same load order as the `.arz`. 20,322 tags against the 16,246 in GrimTools' `l10n/en.js` that this replaced, and current rather than dump-lagged. 13 locales ship with the game; `settings.locale` picks one and the cache is keyed per language (`db-<locale>.json`) with icons shared across them.
- Gendered locales mark grammar inline: a noun opens with what it *is* (`[ms]`, `[np]`), an adjective spells out every form it *could take* (`[ms]искусный[fs]искусная…`). `cleanText` drops the noun's marker and keeps an adjective's first form; real agreement is a backlog item.
- Game version comes from a NUL-terminated `v1.3.0.6` string in `Engine.dll` (unique under a version-shaped, NUL-terminated pattern). Any published dump reports *its own* version and lags the install.
- The game writes saves event-driven and non-atomically: on checksum failure, retry (torn write), then fall back to `player.g00` rotation backups.
- **Never commit game-derived data** (extracted assets, icon PNGs, save copies) — `.gitignore` covers it; keep it that way. Ship code, not data. Game data is © Crate Entertainment; credit them in the UI/README.
- **The difficulty resistance penalty is in the game data and is not uniform.** `records/game/balancingadjustment_mp+difficulty_players01.dbr` (`AttributePak`) holds `defensive*` arrays 12 long = 3 difficulties × 4 player counts; single-player reads index 0/4/8. Ultimate is −50 to Fire/Cold/Lightning/Pierce/Acid, −25 to Aether/Chaos/Vitality/Bleeding, and **0 to Physical**; Elite penalises only the first five. The in-game "−25%/−50% to all resistances" blurb is a simplification — do not hardcode it. Read via `GameDb.difficultyPenalty`.
- **Armour is localized, and absorption is multiplicative.** Every physical hit rolls one body part — Head 15%, Shoulders 15%, Chest 26%, Hands 12%, Legs 20%, Feet 12%, from the `combatRegion*Chance` fields of `records/game/combatformulas.dbr` via `GameDb.combatFormulas()` (the community's 12/12/24/16/20/16 table was hardcoded here for a while and is wrong against the installed build) — and is met by *that piece alone*, so summing the six ratings describes a character who does not exist and hides the weak slot. Flat `+Armor` (`defensiveBonusProtection`, and `defensiveProtection` from anything that is not itself an armour piece — rings, components, skills) is added to **every** part. `defensiveProtection` is therefore context-dependent: a piece's own rating on armour, a character-wide bonus everywhere else. Absorption is `base × (1 + modifier)` capped at 100 — 70 × 1.2 = **84%, not 90%** — with the base in `records/game/gameengine.dbr` (`armorDefensiveAbsorption = 70`; the `records/ingameui/` record of the same name carries a stale 66, ignore it).
- **Absorption and its qualifier flags are one stat.** A skill's `damageAbsorption`/`damageAbsorptionPercent` may sit beside `<type>DamageQualifier` flags (Maiven's Lens: flat 525 + `physicalDamageQualifier`), meaning it absorbs that type only — `statfmt` folds them into one line (`525 Physical Damage Absorption`; DBR dialect applies: `life`→Vitality, `poison`→Acid) and claims zeroed qualifiers as template filler. Rendered apart, the number over-promises and the flag prints raw, which is exactly how the live app once showed it.
- **Negative `defensive<Type>` is always resistance *reduction*, never player defence.** Verified across every player passive and modifier in the game: zero counter-examples. Skill/modifier banding leans on this, which is what makes the parent-lookup heuristic safe (there is no parent pointer in the data — not on the record, not in `_classtree_classNN.dbr`, not in `records/ui/skills/`; stem numbering `veilofshadows2` → `veilofshadows1` is the fallback).
- **Toggled auras and shouts are two records**: a thin activator holding only `buffSkillName`, and the buff that carries every stat *and the display name and max level*. Always follow the hop for stats **and** for naming — `bonechillingcry1.dbr` has neither a name nor a `skillMaxLevel` of its own.
- **Attribute requirements are equation-derived, not stored.** Every item's `strengthRequirement`/`dexterityRequirement`/`intelligenceRequirement` is 0 (one quest item excepted — non-zero is an override). The real values are equation strings in the 13 `records/game/itemcostformulas*.dbr` records (`itemCostName` on the item picks the file; the item's `Class` picks the `chest`/`axe`/`amulet`… key), evaluated at `itemLevel` by `src/core/db/formula.ts`. Naming: strength=Physique, dexterity=Cunning, intelligence=Spirit. Spears ride the `melee2h` equations (no spear keys are populated anywhere); medals genuinely require nothing. Only ring/amulet equations use `totalAttCount` — and its stat count must be whitelisted to `character*/offensive*/defensive*/retaliation*/augment*/skill*` keys, because counting metadata like `itemLevel` inflates a ring's Spirit requirement (~3% of `itemLevel × 3` per phantom key; this bug shipped and the wearing-it gate caught it). **Level requirements are the opposite: always the explicit field** (never `itemLevel`, 516 records differ), and affixes gate too — effective level = `max(base, prefix, suffix)`.
- **`-% Requirement` reductions are a scope × attribute matrix, and the save's attributes are base-only.** Reduction fields are `character<Scope><Attr>ReqReduction` (Global/Armor/Jewelry/Shield/Weapon/Melee/Hunting; additive, Global stacks on scope; `characterLevelReqReduction` is flat levels) — skip zero values, fifteen medals carry the field zeroed. The character's real attributes = save base + mastery-bar cumulative per-rank arrays (`_classtraining_class{NN}.dbr`) + gear/skill `characterStrength`-family flats, × (1 + %). `checkRequirements` reports rather than filters: a reduction or +attribute can come from the very item a swap removes, and post-swap reasoning belongs to the advisor.
- **A component's origin is one decision, so §8 is the single component list**: owned loose, installed in gear, and craftable from a learned blueprint, each with its stats. §10 keeps relics, blueprint purchases and awakening paths only — craftable armour and weapons are noise beside §7's ranked candidates. **Reagent chains resolve transitively**: a component recipe's reagents are often other components the character can make, so `recipeView` crafts what it can from one shared material pool as it descends (cycle-guarded, depth-capped, rolled back when the shared materials run dry). A listed shortfall therefore really is one.
- **Component extraction is either/or destructive, and use-on slots are typed.** The Inventor's salvage (game's own `tagDividing*` strings) recovers *either* the item *or* the installed component — the other is destroyed, and augments are lost in every direction (never recoverable; replacing one costs only the new augment). An item holds up to one component + one augment in independent sockets. Partial components no longer exist in the game (`completedRelicLevel` ≡ 1; the save's `relicCompletionLevel` is legacy). `DbItem.allowedSlots` (components/augments only) is the 23-flag use-on restriction lifted out of `stats` — a socketable may only be proposed for a slot it accepts. Applying an augment **soulbinds** the item (no trade, no transfer stash) until the augment is removed/destroyed.
- **Dual-wield needs an enabler, and the data marks enablement and conditionality with the same flags.** `dualWieldOnly`/`dualRangedOnly = 1` on a skill record means "inert unless dual-wielding"; the enablers are the flagged *plain passives* among invested mastery skills (Dual Blades, Implements of War — flagged WPS/transmuters only require DW) plus any *item-granted* flagged skill (Direwolf Claw, Mutilate, Slaughter's Bloodbath). `aggregate.wielding` computes the mode and names the enablers; a dual-wield mode with none is a model gap. DW-conditional skill stats are excluded outside their mode. **Set counters count distinct members** — a second copy of the same ring adds nothing (in-game verified). **Speed caps** come from `gameengine.dbr` via `GameDb.speedCaps()`: attack/cast 200%, run 135%. The damage ranking does not apply conversion (disclosed in the exclusions; conversion pairs provably stop at suffix 2).
- **Damage conversion is ordered, once-only, and scoped.** A skill's own conversion (record/modifier/transmuter — `Skill_Modifier`/`Skill_Transmuter` nodes belong to the skill they modify, never the character) applies before global conversion from gear and permanent buffs; `+% damage` applies after, to the output type. Damage never chains through a second pair; one in-type drawn past 100% splits proportionally. DoT twins convert together (Physical↔Internal Trauma, Fire↔Burn, Cold↔Frostburn, Lightning↔Electrocute, Acid↔Poison, Vitality↔Vitality Decay); Pierce/Aether/Chaos have no twin (the DoT stays behind); **Bleeding never converts** — no record carries it as an in/out type. The DBR dialect: `Poison`=Acid, `Life`=Vitality, `Elemental` = fire+cold+lightning each (in) / ⅓ split (out), and full-convert transmuters write a semicolon list incl. `Stun` (drop it). **`% Armor Piercing` is implicit conversion**: the base weapon record's own `offensivePierceRatioMin` (all 270 carriers are weapons — no component/affix/skill has it) deals that share of the weapon's *physical* as pierce. Flat gear damage reaches skills only through `% weapon damage`; the aggregate's flats are min–max midpoints with permanent global conversions applied (`applyConversions` in `stats.ts`).
- **Inventory footprints are in the icon, and nowhere else.** No DBR field carries an item's cell size; the engine derives it from the texture at **32 px per cell**, so `getIconInfo` does too (`clamp(round(px / 32), 1, 4)`). The bag grids are engine-side as well — `MAIN_BAG` 12×8, `EXTRA_BAG` 8×8 in `src/core/grid.ts`, corroborated by `_Suchka`'s main bag tiling 96 of 96 cells with zero overlaps and by the game's own `character_inventoryextrapanelimage.tex` being 258×259 (exactly 8×8 cells plus border). `sackDims` still grows a grid to cover its contents, so a wrong constant costs a roomy container, never a lost item.
- **Pet skill subtrees (`records/skills/*/pets/`) are four fifths of the skill data** and are out of scope; indexing them takes `db.json` from 21 MB to 66 MB. Keep them excluded.
- **A granted skill's *kind* is data, not an inference.** Every `Grants: <skill>` line states how you get it, from the record's template class: `passive — always on`, `toggle — stays on until switched off` (`characterManaLimitReserve` shows the reservation in its own stats, and not every toggle has one), `activated — you have to cast it`, `auto-cast <trigger>` (a proc), `weapon-pool proc`, or `summons a pet`. Without it the reader has to guess a buff from the presence of an "Energy Reserved" line, and the classes with `PassiveOn…` (low health, when hit) would read as unconditional. None of these is summed into §3 — named and shown, listed as an exclusion. **And a `Grants:` line stays with the part that carries it.** The dossier always did this; the UI's `buildTooltip` used to lift an installed socketable's grant into the *host item's* block, which cost twice — the component's own panel (its chip, and the one a merely *proposed* component gets) fell silent about the buff that is the whole point of Vicious Spikes or Seal of the Void, and the item was credited with a skill that leaves the moment the component does, which is exactly what a `SWAP-COMPONENT` does. Attributed to the part, it is stated once and in the right place; `test/view.test.ts` asserts the installed copy and the dictionary entry have identical lines.
- **A permanent dual-wield enabler ends the argument.** An invested mastery passive is spent skill points: while one exists no gear swap can end dual wielding, and an item's dual-wield grant is never a reason to keep it. `aggregate.wielding.permanentEnablers` counts them and §4 states the consequence outright; the zero-permanent case is the only one where the constraint is real, and it inverts loudly.
- **Attack speed is attacks-per-second and the weapon term is additive.** The baselines are on the player creature record (`records/creatures/pc/malepc01.dbr`, identical to the female one): `characterAttackSpeed = 1.25`, `characterSpellCastSpeed = 1.25`, `characterRunSpeed = 0.93` — read via `GameDb.baseSpeeds()`, and note `WANTED_PREFIXES` must keep that record or the build silently falls back to defaults. A weapon's `characterBaseAttackSpeed` is an **additive delta in attacks/second** (Very Fast ≈ −0.02, Very Slow ≈ −0.20; observed −0.24…+0.01, one sword outlier at +0.40), **never a percentage** — so a `1.99` is the game's own `tagAttackSpeed = {%.2f} Attacks per Second` display, not "199%". Only the 12 weapon classes carry it; shields and off-hands carry the descriptor tag as template filler with no number, and no item of any class carries a `characterSpellCastSpeed` or `characterRunSpeed`. The char-sheet percentage is the resulting rate **relative to the baseline**, capped on the result (`playerAttackSpeedCapMax` 200, min 20) — which is what `tagCharStatsAttackSpeedDescription` means by "slower weapons gain less from % Attack Speed bonuses": a Very Slow weapon needs ~+148% where a Very Fast one needs ~+102%. Dual wield weights each weapon at `dwWeaponSpeedFactor = 0.5`, i.e. their mean. The **composition is inferred, not quoted** — the caps and bases are records, the way they combine is engine behaviour — so §3 says so. `+% Maximum Movement Speed` raises the *cap*, so 135 is not a constant either.
- **Cunning and Spirit scale damage, Physique does not — and the rates ARE in the game data.** For a long time this file said "engine-side, refuse a number"; a deeper sweep (2026-08-10) overturned that: `records/game/combatformulas.dbr` — the record `gameengine.dbr` wires in as `defaultCombatManagerRecord`, whose every field Game.dll loads by name — carries the formulas as equation strings. `physicalDamageEquation = physicalDamageDV*((dexterityDV/245)+1)` → **0.408%/pt of Cunning for Physical & Pierce**; `/215` for physical DoTs (Bleeding, Internal Trauma) and for Spirit's magical damage → **0.465%/pt**; `/200` for magical DoTs → **0.5%/pt**. There is **no strength damage equation** — Physique's "no damage at all" stands, now as a data fact. `GameDb.combatFormulas()` derives the rates by *evaluating* the equations (never hardcode 245/215/200), §3 states the character's current bonus per type, and the official Game Guide corroborates (0.41/0.46/0.47/0.5 rounded; linear, the base 50 counts). What remains non-data: the physical/magical **group membership** is an enum in Game.dll (the game text names the members — Cunning → Physical, Pierce, Bleeding, Internal Trauma; Spirit → Fire, Cold, Lightning, Acid, Vitality, Aether, Chaos + DoTs), and *how the bonus stacks* is community knowledge (additive with gear's `+%` pool, per the Steam mechanics guide) — the doc attributes that rather than stating it as data. The char sheet's `+%` figures exclude the attribute bonus (`tagCharStatsPhysicalPercentDmgInfo`: "not including the bonus from Cunning"). (`tagCharAttributeIncrement01` claims "increases Cunning by 10" and is **stale**: `playerlevels.dbr` says 8 and so does the game's own tutorial tip. Don't "fix" the code to 10.)
- **Every stat reference in advice must name its kind.** `+99% Pierce` (damage) and `+22 FCL` (resistance) appeared four words apart in the first live answer. `verify.ts` decides this mechanically (`ambiguous-stat`) over the plan's reasons, `gains`/`costs` and the prose; the sign is optional in the pattern because `but costs 35 Acid` carries none. **A label–value list is not a bare stat**: in `Fire 92, Cold 90, Lightning 80` the matcher's `92, Cold` is the seam between two entries, so a type name followed by its own *unsigned* number is exempt — both live runs spent a full repair call on exactly this false alarm, one of which then failed to fix it. A signed number after the type stays flagged (`+48 Pierce, +60 Acid` is two stats), and the exemption is same-line only.
- `claude` CLI invocation: pipe the context doc via **stdin**, use `-p --output-format json --tools "" --no-session-persistence`, cwd = tmpdir. **A real advice call takes ~500s** (measured: 496s and 487s at ~36k tokens in, ~40k out) — the timeout is a 900s runaway ceiling, not an expectation, and the 180s originally planned killed healthy runs. The envelope reports a cached dossier under `cache_creation_input_tokens`/`cache_read_input_tokens`, **not** `input_tokens`; sum all three or the usage line reads "2 in". **Wall time is output tokens** (~90/s at opus, measured across both live runs), and roughly three quarters of them are reasoning — so `usage.thinkingTokens` records the stream's last thinking-phase estimate per call, summed into the envelope, which is what an effort A/B compares two runs by. Never use `--bare` (it disables the subscription OAuth this tool depends on). **Always pin `--model` and `--effort`** — both flags exist on the installed CLI, and without them the subprocess inherits whatever the user's interactive session or settings specify, which makes two runs on the same save silently incomparable. **The defaults are `opus` at `medium` effort**, settled by a live A/B against high (2026-08-10): same core moves, every socket filled, every resistance capped *sooner* — high's extra ~15k thinking tokens bought a maximum-damage line that left Chaos Resistance 11 under cap for two levels — at 22% less wall time ($2.22/540s vs $2.59/696s). High stays available in settings; the effort tiers are described to the user in the settings pane, medium marked recommended.
- **`codex` CLI invocation (the `codex-cli` backend, ChatGPT subscription):** `codex exec --json --ephemeral --skip-git-repo-check --ignore-user-config -s read-only --color never -c model_reasoning_summary=detailed -c web_search=disabled -m <model> -c model_reasoning_effort=<effort> <SYSTEM_PROMPT>`, dossier over **stdin** (codex appends it as its own `<stdin>` block — there is no `--system-prompt` flag, so the prompt argument carries the persona), cwd = tmpdir. Auth is the user's own `codex login`; the OAuth flow Zed made famous is this same CLI's auth re-implemented, so the CLI *is* the integration — no token code in this repo. **`--ignore-user-config` is required, not hygiene**: `~/.codex/config.toml` injects warnings as `error` items into the stream and can spin up MCP servers. **`-c model_reasoning_summary=detailed` is what makes reasoning exist in the stream at all** — it arrives as whole `item.completed` summary blocks, not token deltas, and usage lands once on `turn.completed` (`reasoning_output_tokens` → `thinkingTokens`; `cached_input_tokens` is a **subset** of `input_tokens`, so never sum them — the opposite of claude's three disjoint fields). A subscription run has no dollar figure: `costUsd` stays **absent** (envelope-optional), rendered "included in the subscription", never 0. Defaults `gpt-5.6-sol` at `medium` — model chosen by the user, medium confirmed by a live A/B against high (2026-08-10, pre-fast-mode): identical equips and fills, every resistance capped in both, high's extra ~9.5k thinking tokens (668s vs 440s) bought only augment re-shuffles among the same powders, and high's first draft carried *more* warnings (2 vs 1, incl. `unaddressed-item`). Effort names are the Responses API's enum, **not** claude's: `none` through `max`, plus `ultra` on the 5.6 models; `minimal` is rejected there and `fast` does not exist (all verified live). **`none` is deliberately not offered** — the settings floor is `low`, because a no-reasoning advisory answer is a plan you act on blind. **Fast mode (`-c service_tier=fast`, the renamed "priority processing") defaults to on** (`codexFast` in settings, absent = true; CLI `--no-fast`): included in the ChatGPT subscription, ~2× the credit burn, verified live — and codex-only, because claude's fast mode bills API usage on top of the subscription. Per-backend defaults resolve through `providerDefaults` in `src/core/ai/index.ts` — the old call sites handed claude's `opus` to whatever backend was named.
- **Components and augments carry dossier ids too, and every plan reference gives id *and* name.** Socketables have no save instance, so their identity is the record path — `shortHash(record)` from `resolve.ts`, same alphabet and width as an item id, reserved against the item ids so the two spaces never collide. That retired the strip-the-parenthetical name matching in `verify.ts` (`nameWithoutQualifier` survives only as the fallback for an answer that gave no id). The plan carries `itemName`/`targetId`/`targetName` beside the ids **on purpose**: a right name paired with a wrong id is the one failure an id-only plan hides, because both halves of the answer look internally consistent — `name-mismatch` is the check.
- **The prose does not contain a per-slot table; the tool renders it.** The model was writing one and the CLI was rendering its own from the plan, so the terminal printed it twice and the two could disagree. The prompt now forbids the prose table, and `advise -o` appends the rendered one so a saved answer stands alone. Related, and **measured rather than assumed**: splitting prose and JSON into two calls is not cheaper — the JSON is ~2.7k of ~30k output tokens (≈$0.20 of a $3.70 run), a second Opus call costs more than it saves and a Sonnet one saves ~4%, and an extractor without the dossier **cannot resolve ids at all**, which is the entire reason the plan block exists.
- **The repair loop is exactly one call, it runs cheaper than the first, and it keeps whichever answer is cleaner.** `checkPlan`'s warnings are fed back once; a revision that comes back no better is discarded and the original shown, because a loop that can trade three warnings for four is a coin flip rather than a repair. `--no-repair` opts out. The cost line covers both calls whichever wins. Two economies added after the first live runs, both measured rather than assumed: **prose-only warnings never trigger the call** (`worthRepairing` — both live runs spent a second full-price call, six minutes and ~$2 each, on nothing but `ambiguous-stat`, and one revision then failed to fix it; wording is reported to the user and left standing) and **the corrective call runs at `repairEffort`** (high/xhigh/max → medium — a repair is an edit, "fix exactly what the checks name, keep everything else", not fresh optimisation, and keep-whichever-is-cleaner already guards a worse revision).
- **The context document's size is bounded by the candidate level window, not by a token budget.** Everything a normally-stocked character can reach is ~36k tokens; a bigger budget changes nothing about the file. The 100k default exists for oversized stashes, where the per-slot cap would otherwise start discarding real candidates. Don't "optimize" the doc down — trimming a candidate is a real loss of information and the receiving model has a 1M-token window. The one *user-chosen* reduction is the **stash toggle** (`includeStashInAdvice`, default include; header checkbox, CLI `--no-stash`): `adviceScope` filters the stored items out of the resolved walk and rebuilds the document, which removes them from every section at once. The **materials store always ships** — it is the component census, not a container of gear — and the **UI snapshot is never filtered**: a preference about what the model reads must not make items vanish from the screen. The envelope records `stashIncluded` because scope is part of an answer's identity.
- **Dispositions are exhaustive for the carried bags, and the stash is off the sell list.** The player put stash items there on purpose, so a plan may recommend wearing or holding one but never selling it (`sell-in-stash`); and every piece of gear the document offers from the bags — §7's ranked candidates plus its "Carried but unranked" line, which names the under-window junk precisely so it *can* be dispositioned — must end in a verdict, `hold` or `sell` (`unaddressed-item`, measured against `ContextDoc.candidateIds`: an item the model was never shown cannot be demanded a verdict on). Both rules live in the prompt *and* in `checkPlan`, so the repair loop enforces them. An unlock in `nextLevels` the model recommends acting on must also appear in `hold`; one it advises skipping says so in its recommendation — an unheld next-level item is a decision, not an omission. **An empty component socket the plan walks past is checked the same way** (`unfilled-socket`): the slot's post-plan item — the candidate for an `EQUIP` — with an empty component socket, while `ContextDoc.freeComponentIds` (loose on hand or craftable now; an installed-only copy costs its host) offers a legal fill, must receive a component through its verdict or `fits`, or argue its emptiness. This is the thoroughness failure a lower reasoning effort was observed to make, decided mechanically so the effort knob stops deciding it.
