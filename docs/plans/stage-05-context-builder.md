# Stage 5B — Context document builder

> Depends on Stage 5A (mechanics layer), 5A.2 (requirements & attributes), 5A.3 (socketable use-on slots), 5A.4 (wielding modes, speed caps) and 5A.5 (damage-type path): the resistance matrix, damage profile (conversion-aware, with `weaponAttack` composition and per-skill `skillDamage` typing), skill/devotion/set/affix data, attribute totals, requirement reductions, per-item requirements, `DbItem.allowedSlots`, `aggregate.wielding` and `GameDb.speedCaps()` all come from there. This stage renders; it does not compute game mechanics.

## Goal

Compile everything the tool knows into a single markdown "context document" sized for an LLM (~≤30k tokens), via CLI `context --char <name> [--difficulty N]`. This document *is* the AI prompt payload (Stage 6) and a debuggable artifact in its own right.

The design bar: **the advisor must be able to reason holistically from this document alone.** Concretely, all of these must be answerable from the doc without outside knowledge: "if I equip these legs, which augments become redundant and what do I re-slot?", "is +50% pierce damage worth more than +10% chaos res *for this build*?", "which resistance holes are real once buffs are counted, and which totals are fragile because they lean on a duration buff?". The model's own memory of Grim Dawn may predate v1.3/Fangs of Asterkarn — every rule it needs must be stated in the doc.

Format choice is **markdown, not JSON**: human-form stat lines cost fewer tokens than raw key/value JSON and the doc doubles as something the user can read (`npm run cli -- context > doc.md`).

## Document sections (in order)

1. **Header** — name, level, class combo (from the save's `tagSkillClassName*` tag, e.g. "Blademaster"; fall back to the two mastery names), difficulty (from save block 1; `--difficulty`/settings override wins), hardcore flag, iron, game version.
2. **Game rules** (static, self-contained — do not rely on model memory): resistance cap 80 (hard cap 95 via +max-resist), the difficulty penalty **per resistance as `GameDb.difficultyPenalty` reports it** (it is not uniform — Ultimate is −50 elemental/pierce/acid, −25 aether/chaos/vitality/bleeding, 0 physical; render the actual vector, never the in-game "−50 to all" blurb), recommended overcap +20–30 on primary resists against enemy resist reduction, faction market tiers and thresholds. **Socketable rules** (verbatim-verified against the game's own Inventor UI strings, `tagDividing*` in `Text_EN.arc`): an item carries up to one component *and* one augment — independent sockets, independent moves. Every component and augment has a use-on restriction (`DbItem.allowedSlots`) and may only be proposed for gear that restriction accepts. Applying a loose socketable to an *empty* socket is free and instant; augments are consumables bought with iron — treat every augment slot as a free variable, since replacing one costs only the new augment (removal always destroys the old augment, never recovers it). Occupied component sockets go through the Inventor's salvage, an either/or with an iron fee: **keep the item → the installed component is destroyed** (and augments removed) — so upgrading a kept item's component is a first-class move costing the old component + fee + a fresh augment; **keep the component → the host item is destroyed** (and its augments) — so a single-instance component *can* move to new gear at the price of the old item. **Requirement rules:** items demand character level and Physique/Cunning/Spirit; `-% Requirement` reductions stack additively and are scoped by gear family (Global on top); a reduction or +attribute granted by an item vanishes if that item is swapped out, so joint moves must be re-checked; one unspent attribute point = 8 of any attribute; a level or attribute deficit that levelling or unspent points will close is a **HOLD-until**, not a reject. **Speed caps** (render from `GameDb.speedCaps()`, engine record values): attack 200%, cast 200%, movement 135% — `+% speed` on a build already at a cap is worth nothing; do not trade real stats for it. **Dual-wield rule:** dual wielding requires an enabler (a mastery passive or an item-granted skill — the doc states which the character has, from `aggregate.wielding`); a swap that removes the *last* enabler while leaving two one-handers is illegal. **Soulbound:** applying an augment soulbinds the item — it cannot be traded or placed in the transfer stash until the augment is removed (which destroys the augment). **Respec economy:** skill points refund at the Spirit Guide for iron (cost rises, caps at 15k/point) and the mastery bar can be reduced, but the class combination is permanent; attribute points refund only via the scarce Tonic of Reshaping (two from quests, then craftable at hidden Celestial Blacksmiths in Elite/Ultimate) — so an attribute respec is a build decision to flag for an exceptional item, never a routine move. **Damage conversion rules** (engine-verified; the profile already applies them to its flat figures, and the advisor must apply them when judging any candidate): conversion order is skill's own conversion (its record, modifiers, transmuters) first, then global conversion from equipment and permanent buffs, and `+% damage` modifiers apply *after* conversion, to the output type — so a converted build is served by modifiers of the output type, not the input. Damage is only ever converted once (never chained); conversions of one in-type past 100% split the pool proportionally. A converting type takes its damage-over-time twin along (Physical↔Internal Trauma, Fire↔Burn, Cold↔Frostburn, Lightning↔Electrocute, Acid↔Poison, Vitality↔Vitality Decay); Pierce, Aether and Chaos have no twin, so the DoT part stays unconverted; Bleeding never converts at all. `Elemental` as an in-type converts fire, cold *and* lightning each at the stated %; as an out-type it splits evenly three ways; flat Elemental damage is a third of each element, and `+% Elemental` boosts all three (but not their DoTs). **`% Armor Piercing` on a weapon deals that share of the weapon's physical damage as pierce** — physical only, the weapon's own ratio only. **Flat damage on gear applies only to weapon attacks** (the default attack and any skill's `% Weapon Damage` component) — it does not raise skills without a weapon component; the doc's weapon-attack composition line is what those flats describe. A candidate's own conversion can *be* its damage-type fit: a 100%-physical→pierce gun is a pierce weapon.
3. **Attributes & defenses** — from `aggregate.attributes`: physique/cunning/spirit each as base + gear/skill flat + % = total (+ unspent points), health, energy, OA/DA contributions (with 5A.2's caveat that the engine's level/attribute-derived base is not modelled), the requirement-reduction matrix (`aggregate.requirementReductions` — scope, attribute, %, source), the 5A defense summary (per-part armor, shield block, sustain); then the **resistance matrix** from Stage 5A verbatim in table form: one row per source (each equipped slot split into base/affix/component/augment contributions, set bonuses, each counted skill/devotion node), the three summary bands (permanent / +maintainable / effective vs cap at this difficulty), the exclusions list, and per-resistance overcap or shortfall numbers.
4. **Skills, devotion & build profile** — mastery point split, unspent skill and devotion points; each skill with ≥1 point: name, rank shown as invested + gear bonus = effective ("12 +4 = 16/22"), one stat line evaluated **at the effective rank** (damage or buff essentials — this is what the skill actually does right now), weapon requirement when restricted ("requires: two-handed melee"), transmuters and modifiers attached to it; devotion constellations with their passive stats, celestial powers and what each is bound to (`autoCastSkill` bindings); then the **damage profile**: ranked damage types with summed % modifiers and **post-conversion** flat figures (midpoints), each global conversion line with its source and scope ("30% Elemental → Pierce — Chosen Epaulets, global"), resist-reduction sources. Render the **weapon-attack composition** (`damage.weaponAttack`: "weapon attack: 57% pierce · 32% bleeding · 10% frostburn", main attack named when a default-attack replacer is invested) and the **per-skill damage typing** (`damage.skillDamage`: each invested attack skill with rank, `% weapon damage`, its own flat types, and its skill-scoped conversions marked "this skill only" — a transmuter's conversion belongs to its skill, never to the character). State the **wielding mode and its enablers** from `aggregate.wielding` ("dual-wield melee — enabled by Dual Blades; Bloodbath, granted by Slaughter"), so the advisor can see which items/skills a weapon-change must preserve. End with one computed sentence: "Build focus: <top-2 damage types>" — the post-conversion path every candidate's damage stats are judged against.
5. **Equipped** — one compact block per slot: **item ID** (see below), display name, rarity, requirements from `ResolvedItem.requirements` (level incl. affix gates + Physique/Cunning/Spirit), set membership ("Deathmarked, 2/4 equipped"), base stat lines, affix stat lines (marked as base roll ± jitter), component (+ rolled completion bonus; partial components no longer exist in the game, so there is no completion state), granted skill if any ("Grants: Mutilate"), augment (name + faction + cost). Explicitly call out empty component sockets and missing augments — prime recommendations. Both weapon sets, active one marked; advise for the active set, treat the other as candidates.
6. **Set status** — for each set with ≥1 piece equipped or owned: pieces equipped/owned/missing, active bonus now, bonus at next piece count (so "complete the set" is a visible move; so is "breaking this set loses X").
7. **Candidates** — inventory + personal stash + transfer stash, grouped by equip slot, each with its **item ID** and tagged `[inv]`/`[stash]`/`[transfer]`, with base *and affix* stat lines, its requirements, and a **requirement annotation** computed via `checkRequirements` against the aggregate: `meets`, `short 42 physique (have 558, need 600)`, or `needs level 84 (HOLD)`. Weapons additionally carry a **damage identity** line: base damage types with armor piercing applied ("deals 92–103 pierce (100% armor piercing)"), and any conversion the item itself grants — a candidate whose damage or conversion misses the build's post-conversion top types is marked `off-type`, and one whose conversion *feeds* a top type counts as matching. Failing candidates are data, not garbage — the advisor decides between enabler combos, HOLD-until, and discard. A candidate's own installed component/augment renders like an equipped item's — and feeds the §8 census, because a candidate can be an extraction *source*. Filtered (below).
8. **Component census & crafting materials on hand** — a census over *all* containers, because "the only copy lives inside an old item" must be visible. For each distinct component the character owns anywhere: loose count by location (`[inv]`/`[stash]`/`[transfer]`), installed hosts by **item ID** (equipped incl. both weapon sets, and candidates), its use-on slots (rendered readably from `allowedSlots`), and a craftable-now flag (reuses §10's blueprint + materials check). A component whose only instance is installed is explicitly marked: `single instance — extraction destroys <host itemId>`. Augments: loose ones on hand with counts and use-on slots (installed augments render per-item in §5/§7 and are never recoverable). Plus counts of notable crafting materials (Awakening Ashes and the other `crafting/materials/` items) so upgrade affordability is checkable.
9. **Available faction augments** — per faction the character has unlocked: only tiers actually reached, only level-appropriate augments; name, one stat line, **use-on restriction** (from `allowedSlots`), iron cost. Note current iron on hand (header) makes affordability checkable.
10. **Blueprints & upgrade paths** — learned (formulas.gst) relic/gear/component recipes within level range, each with reagent requirements and a computed **craftable-now** flag (checked against materials on hand + iron; if not, list what's missing); purchasable faction blueprints at reached tiers, marked "purchasable at <faction>"; and for any equipped or candidate item whose record is the `baseReagent` of an awakening recipe, a note: "Awakened version exists — requires 12× Awakening Ashes + …" (a strong HOLD signal even when currently unaffordable). State the game rule that ascension (random ascended affix) exists, is expensive, and is a gamble — the advisor may mention it, never prescribe rerolling.
11. **Task** — the instruction block (kept in sync with the Stage 6 system prompt, which carries the full procedure): recommend per-slot **KEEP / EQUIP <candidate> / RE-AUGMENT <name> / ADD-COMPONENT <name> / BUY-AUGMENT <name> / CRAFT <blueprint>**, a HOLD list, a SELL/SALVAGE list; optimize the loadout *as a whole* (gear + component + augment assignment together), not slot-by-slot in isolation; state reasoning; finish with a projected resistance table after all recommended changes.

**Item IDs.** Every item the advisor may reference (equipped, candidates, socketables) gets a short stable ID printed with it (`#a3f`), derived from `(record, seed)` with a location disambiguator for true duplicates. Names are ambiguous — two rings can share an identical name — and Stage 6's structured output plus Stage 7's UI highlighting both key on these IDs. `ResolvedItem` carries the ID so the renderer and the UI derive it identically.

## Filtering heuristics (`filters.ts`)

- Candidates: equippable gear only; level req (the affix-inclusive `requirements.level`) ≤ charLevel + 10 and ≥ charLevel − 25 — the over-level window exists because "HOLD until level N" is advice worth giving; drop Common rarity when charLevel > 30 **unless** its affixes cover a current resistance shortfall (a yellow with the right resist suffix can be the correct answer); cap ~8 per slot ranked by a relevance score: covers-a-shortfall > matches top-2 damage types (judged post-conversion — the item's own conversion and armor piercing count toward the match) > rarity > level proximity.
- Attribute requirements never hard-filter on their own, but they demote: a candidate whose deficit exceeds what unspent points (× 8) plus ~15% plausible gear support could cover ranks last and is the first cut under token pressure — for this character it is a stat-stick, and SELL is the advisor's call to make, not the filter's.
- Soft class-relevance: don't hard-filter weapon types (GD builds are weird); when over token budget drop caster off-hands for pure-melee mastery pairs and vice versa.
- Token gate: `estimateTokens(doc) ≈ chars / 3.6`; if > 30k, progressively tighten candidate caps (8→5→3), then compress section 10 to counts, then drop section 8's partial components — never touch the matrix, skills, or equipped sections.

## Stat formatting (`statfmt.ts`)

Map the most common DBR stat keys to templates: `defensiveFire` → `+{v}% Fire Resistance`, `characterOffensiveAbility` → `+{v} Offensive Ability`, `offensiveChaosModifier` → `+{v}% Chaos Damage`, min/max pairs → `{min}–{max} Fire Damage`, `…Chance` variants → `{c}% chance of …`, conversion keys (`{v}% {from} Damage converted to {to}` — use the normalized names the profile uses, Vitality/Acid not Life/Poison), `offensivePierceRatioMin` → `{v}% Armor Piercing`, retaliation keys, racial-damage keys. The **skill-reference families** render via the 5A name map, never as raw paths: `augmentSkillName{i}/Level{i}` → `+{n} to {skill}`, `augmentMasteryName{i}/Level{i}` → `+{n} to all skills in {mastery}`, `augmentAllLevel` → `+{n} to all skills`, `itemSkillName` → `Grants: {skill}`, and `modifiedSkillName{i}`+`modifierSkillName{i}` → `Modifies: {skill}` — expanded with the modifier record's notable stat lines **when the character has points in the modified skill** (that's how an awakened item's or ascended affix's real value shows), collapsed to the name otherwise. Build the table by scanning distinct keys actually present for the items/skills in our saves rather than guessing. **Unknown keys fall back to `` `key: value` ``** — never silently drop a stat. Know the flat-vs-% semantics: `defensive*` resist keys are %, `character*` mostly flat, `*Modifier` suffix means %.

## Acceptance criteria

1. `npm run cli -- context --char _Suchka` emits well-formed markdown with all 11 sections; token estimate printed and ≤ the budget. *(Amended during the stage: the default budget is 100k and the document lands at ~36k untrimmed — see the Outcome. A test still asserts it fits 30k when a caller asks for that.)*
2. The resistance matrix in the doc matches `aggregates --char _Suchka` exactly (same numbers, one renderer test asserts this).
3. Section 9 lists **only** factions/tiers the save's rep values actually reach (unit test at exact threshold boundaries: 1500 vs 1501), each augment with a use-on restriction.
4. Difficulty: auto-detected value shown; `--difficulty elite` (names and 0/1/2 accepted) overrides and is reflected in header, matrix cap math, and task section.
5. Equipped stat lines are human-readable — spot-check 2–3 equipped items of _Suchka against grimtools item pages, *including one affix's stats on a magical/rare item*; no equipped item renders only raw `key: value` fallbacks.
6. Empty component sockets / missing augments on equipped gear are explicitly called out.
6b. Every equipped block and every candidate shows its requirements; at least one candidate's annotation (a `short N <attr>` or `needs level N` line) is spot-checked against grimtools or in-game.
6c. The census is honest about scarcity: at least one component `_Suchka` owns only as an installed copy is marked `single instance — extraction destroys <host>` with the right host ID (spot-check in game or GD Stash), and every census entry shows use-on slots.
7. The self-containment test: hand the doc (not the game) to a person or model and have them answer the three questions in the Goal — each answerable from the doc text alone.
8. `npm test` + `npm run typecheck` green.

## Outcome

Done. `npm run cli -- context --char _Suchka` emits the eleven sections at **~29.5k tokens** with one trim step (candidates 8 → 5 per slot); all 199 tests and `typecheck` are green. Deliverables landed as planned (`builder.ts`, `filters.ts`, `statfmt.ts`, `context` CLI, `test/context.test.ts`) plus five things the plan did not anticipate.

**The save's faction slot order was wrong, and §9 could not have been correct without fixing it.** `src/core/save/factions.ts` carried guessed names, and Stage 1 had already flagged that the guesses were self-contradictory (Kymon's Chosen and Order of Death's Vigil both Honored, which the game makes mutually exclusive). The order is *not* in the game data — `gamefactions.dbr` holds the roster as a set of keys and the `.arz` stores fields alphabetically — so it was derived empirically from the two live saves: the eight non-`User` factions fill slots 0–7, and `factionUser<N>` sits at slot **N + 6**. Five independent checks agree: every hostile slot is an enemy faction (Beasts, Arkovian Undead, Aetherial Vanguard, Eldritch Horrors, Bloodbound), every never-unlocked slot is one with no reputation to earn (Players, Neutral NPCs, Traps, The Dread, Asterkarn Dead), the Kymon/Death's Vigil contradiction resolves (slot 11 Honored, slot 14 hostile), and `_Suchka`'s three worn Wight Skin Powders are a Kurn augment sold only at Honored — Kurn is `factionUser17` → slot 23, which reads 13,643. The file now maps slot → `DbFaction.id`, so a save slot joins straight onto the vendor stock.

**Two data-layer fixes (schema 8 → 9).** `extractStats` dropped every array, which cost `racialBonusRace` — the runestone's "+8% Damage to Aetherials and Aether Corruptions" rendered as "+8% Damage to certain enemies". String arrays are now kept for a whitelisted key. `petBonusName` was also being dropped as an unlisted record reference, which made several faction augments (Rifthound Salts, Mogdrogen's Blessing) render as having no stats at all; it is kept and rendered as "grants a pet bonus (out of scope)", which is honest rather than blank.

**`db.skillName` cannot answer for every skill reference, and the plan assumed it could.** The records items point at with `+N to <skill>` are often the *buff* half of a two-record skill (`veilofshadows1.dbr`, `item_eyeofthaddeus.dbr`) and carry no display tag — the name is on the record the activator hops to. `statfmt.skillDisplayName` follows the same hop `skillLabel` does. Pet subtree records are named as "a pet skill (out of scope)" rather than as a path, since Stage 5A excluded them from the index on purpose.

**"Never silently drop a stat" needed a plumbing list to be usable.** The 333 distinct keys across both characters' items and skills include ragdoll physics, quest wiring, mesh names and template filler. Those are dropped by an explicit list; everything else that is unrecognised still prints as `` `key: value` ``. The document currently emits **zero** raw fallbacks, so the list is complete against the live data rather than merely large. One key earned a special case: `characterBaseAttackSpeedTag` is meaningful only on weapons and is template filler on all 300-odd armour records, so it is rendered on the item's own header line instead of as a stat.

**The candidate ranking is lexicographic, not additive.** The plan's order ("covers-a-shortfall > matches top-2 damage types > rarity > level proximity") is a strict priority, and a summed score let two rarity steps outrank a resistance hole. Weights now step by orders of magnitude. `damageIdentity` also tracks min and max separately rather than the aggregate's midpoint, since §7 quotes the range a player would see.

**The token gate turned out to be the wrong shape, and the defaults moved.** The plan's 30k was written as a ceiling; measurement showed it is a *floor* on what the document is worth. The whole reachable candidate set — every gear item in the −25/+10 level window, with no per-slot cap — costs **~36k tokens**, and the document cannot grow past that without widening the window itself. At 30k the gate was therefore discarding real candidates (8 → 5 per slot, 22 main-hand weapons unlisted) to hit a number nothing was paying for, while the receiving model has a 1M-token window.

So the defaults are now `maxTokens: 100_000` and `perGroup: 40`, and `_Suchka`'s document renders at ~36.2k with **nothing trimmed**. The budget is a safety net for the hoarder case — a transfer stash several times the test character's, where the cap does bite — not a target. The trim ladder (12 → 8 → 5 → 3, then compress §10, then §8) is unchanged and still never touches the matrix, the skills or the equipped blocks. `--max-tokens` / `--candidates` remain CLI options, and a test asserts the builder can still hit the plan's 30k on demand, since a smaller-context provider would ask for exactly that. Stage 6 should pass its own budget rather than inherit either number.

**§11 asks for a full projected "after" summary, not just resistances.** The plan named a projected resistance table; a swap also moves armour (one body part at a time), health, OA/DA, attribute totals — and therefore whether the *rest* of the loadout still meets its requirements — the damage profile, and skill ranks (which shift every stat read at that rank, including resistances already counted). All are now required of the advisor, with an instruction to say when a figure is not derivable from the document rather than estimating silently.

Spot-checks against the game's own records (better than grimtools, which lags the install): Bloodborn Sabre (`gdx3 …/c017_sword.dbr`) renders all eleven of its fields exactly — 82–96 physical, 16 pierce, +85% pierce, +85% bleeding, 100% armor piercing, +8% attack speed, +66 OA, four `+2 to <skill>` lines, and Ring of Steel auto-cast on crit at 33%; the rare ring's suffix `of Untamed Fangs` (`b_ar308_ar_a.dbr`) renders all five. `Chestguard of Justice` annotates as `short 128 physique (have 593, needs 721)`, which matches §3's physique total. Five components `_Suchka` owns only as installed copies are marked `single instance — extraction destroys #<host>`.
