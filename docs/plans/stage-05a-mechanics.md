# Stage 5A — Game mechanics layer (skills, devotion, sets, affix stats, aggregates)

## Goal

Give the advisor real numbers for everything that contributes to defense and damage, not just item base stats. Today the DB indexes `records/items/` only, and the resolver resolves affix *names* only. This stage teaches the DB about skill/devotion/set records and affix stats, then computes per-character aggregates — a per-source **resistance matrix** and a **build damage profile** — that Stage 5B renders into the context document.

The motivating scenario (from the user): legs with +30% chaos/aether res should let the advisor drop the aether/chaos faction augments from both rings and repurpose those two slots for a different hole or for damage. That reasoning needs (a) each source's exact contribution, separately attributable, (b) skill/devotion buffs in the totals so "holes" are real and not artifacts of an item-only sum, and (c) the build's damage types quantified so a +50% pierce amulet beats a +10% resistance one on a pierce/bleed build.

## Verified format facts (probed against the installed 1.3.0.6 archives — trust these)

- Player mastery skills live in `records/skills/playerclass01..10/*.dbr` (10 = Berserker, gdx3). Devotion nodes in `records/skills/devotion/*.dbr` — Class `Skill_Passive`, `skillMaxLevel = 1`, stats directly on the record, `skillDisplayName` tags like `tagDevotion_B10`.
- Skill stats sit on the record as scalars or **per-rank arrays**: `characterOffensiveAbility = [10,20,29,…] (len 22)`. `skillMaxLevel` (e.g. 12) and `skillUltimateLevel` (e.g. 22) bound the rank; value at learned rank L = `array[L-1]` (clamp to length; scalars apply at every rank).
- Names/descriptions are l10n tags: `skillDisplayName` / `skillBaseDescription`, resolved via the same `Text_<LOCALE>.arc` tables as items. Mastery display names come from the `_classtraining_classNN.dbr` records; the save already carries the combo tag (`tagSkillClassName0410`).
- The template `Class` field classifies behavior. Observed values: `Skill_Mastery`, `Skill_Passive`, `SkillBuff_Passive`, `Skill_BuffSelfToggled`, `Skill_BuffRadiusToggled`, `Skill_BuffAttackRadiusToggled`, `Skill_BuffSelfDuration`, `SkillSecondary_BuffSelfDuration`, `Skill_PassiveOnLifeBuffSelf` (circuit breakers), `SkillBuff_Debuf`, `Skill_Modifier`, `Skill_Transmuter`, many `Skill_Attack*`.
- **Weapon requirements on attack skills**: the per-weapon boolean fields (`Axe`, `Sword2h`, `Ranged1h`, `Offhand`, `Shield`, …) are an *allowed-weapon whitelist when any are set*; all-zero means unrestricted. Only ~13 player attack skills are restricted, but they are build-defining ones (verified: Savage Strike → 2h only, Shadow Strike/Blade Arc/Blitz → melee, Aether Ray → caster off-hand). Carry the whitelist on `DbSkill` — a weapon-swap recommendation that bricks the main attack skill is the worst possible advice.
- Some activated skills keep their numbers on a second record referenced by `buffSkillName` — follow one hop and classify by the **target** record's Class. Pneumatic Burst (`playerclass04/nightbladeenchant1.dbr`, `Skill_BuffSelfDuration`) holds stats directly: `skillActiveDuration = 60`, `skillCooldownTime = 8`.
- **Sign/direction trap:** enemy-facing records (`SkillBuff_Debuf`) carry *negative* `defensive*` arrays — that is resistance *reduction* (e.g. Night's Chill, `veilofshadows2.dbr`, `defensiveCold = [-3,-6,…]`). Never add these to player totals; surface them in the damage profile as RR utility instead.
- Modifier nodes (`Skill_Modifier` — e.g. Elemental Awakening on Pneumatic Burst) carry their own per-rank stats but **no parent pointer on the record**; parent linkage lives in the mastery-tree UI records (`records/ui/skills/classNN/…`) — verify the exact field at implementation; fallback heuristic: record-stem numbering (`nightbladeenchant1` → `…enchant3`). A modifier inherits its parent's bucket (a modifier of a maintainable buff is maintainable; a modifier of an enemy debuff is RR, not defense).
- Item sets: `templateName = database/templates/itemset.tpl` (the `Class` field is **empty** — key on `templateName`), fields `setName` (tag), `setMembers` (record list), bonuses as arrays indexed by equipped-piece count (verify the exact indexing convention at implementation; Wildcaller has `augmentSkillLevel1 = [0,3,3]` with 3 members).
- Affix records (`lootrandomizer.tpl`) carry **deterministic stat fields** (`offensiveLifeModifier = 49`, resist stats, …) plus `lootRandomizerJitter` = ±% roll variance. Expose the stats; label them base values ± jitter. This closes the biggest gap in the item-only sum: on magical/rare gear the affixes often *are* the resistances.
- Relics (`ItemArtifact`) and components (`ItemRelic`) are **already indexed** — the item class regex (`/^(Armor|Weapon|Item|…)/`) covers them. What's missing is around their edges:
  - **Completion bonuses**: the save stores the rolled bonus on `ItemInstance.relicBonus` (parsed since Stage 1, dropped by the resolver). The bonus records (`records/items/lootaffixes/completion*/…`) are Class `LootRandomizer` — i.e. plain affix records, so the affix-stats work above covers their stats for free; the resolver just has to resolve `relicBonus` through `getAffix` and attribute it to the component/relic contribution.
  - **Granted skills**: relics and some components grant a skill via `itemSkillName` (+ `itemSkillLevelEq`), pointing into `records/skills/itemskills/…` (e.g. Blademaster Talisman → `relic_mutilate.dbr`). Index one-hop `itemSkillName` targets so the doc can say "Grants: Mutilate" — *name only*; aggregating granted-skill stats stays on the backlog.
- **+skills rank rule** (in scope — it moves both attack and defense): `+N to <skill>` bonuses apply **only to skills with ≥1 invested point** (GD grants no D2-style oskills via +N; item-*granted* actives are the separate `itemSkillName` mechanism above), stack additively from every equipped source (item base, affixes, components, augments, set bonuses: `augmentSkillName{i}/Level{i}`, `augmentMasteryName{i}/Level{i}` for the mastery-wide bonus, `augmentAllLevel` for all-skills), and the effective rank is clamped to `skillUltimateLevel`. All the source data is already in the indexed stats — effective rank is a small fold over it.
- **Awakened items (gdx3)** are ordinary item records under `records/items/awakened/…` with normal Armor/Weapon classes — **already indexed** (the class regex, not the path, decides). Their distinctive payload is skill-modifier pairs: `modifiedSkillName1..N` (which skill) + `modifierSkillName1..N` (a `Skill_Modifier` record under `records/skills/itemskillsgdx3/skillmodifiers/awakened/…` holding the actual stats).
- **Ascended affixes (gdx3)** are ordinary `LootRandomizer` records under `records/items/lootaffixes/ascended/…` — already in the affix map; the affix-stats work covers them. They also carry `+N to <skill>` (`augmentSkillName1/augmentSkillLevel1`) and skill-modifier references. The Ascendant Altar's affix *swap tables* (`ascensionaffixswaplists/`, `ascensionaltaraffixswap.tpl`) are only needed to advise "this affix could be ascended" — backlog, not this stage.
- **Awakening is deterministic; ascension is a weighted gamble** — this asymmetry must shape advice:
  - Awakening blueprints (`records/items/crafting/blueprints/awakened/…`) are ordinary `ItemArtifactFormula` records (already matched by the recipe builder): `reagentBaseBaseName` (the base item) + `reagent1..N` (e.g. 12× `craft_awakeningashes.dbr` + a component) + `artifactCreationCost` (200k iron) → `artifactName` = one specific awakened item. The base→awakened upgrade path is therefore derivable: recipe whose `reagentBaseBaseName` = this item.
  - Ascension formulas (`records/items/crafting/blueprints/ascension/…`, Class `ItemAscensionFormula` — a *different* class the recipe builder currently skips) roll a random ascended affix from per-slot-type tables with `affixWeight`/`masteryWeight` (600/400 observed), consuming five material types + 250k iron; dedicated reroll formulas (`ItemAscensionFormula`/`ItemRerollFormula` under `blueprints/reroll/`) exist. **Random outcome + high cost ⇒ never advise "ascend until you get X".**
  - Crafting materials (Awakening Ashes etc., `records/items/crafting/materials/`) are ordinary items — already indexed and already resolved when sitting in bags/stash, so availability is checkable.
- **The +skills / skill-modifier field families** appear on items and affixes alike and `extractStats` already keeps them (raw record paths): `augmentSkillName1..N`/`augmentSkillLevel1..N` (+N to skill), `augmentMasteryName1..N`/`augmentMasteryLevel1..N` (+N to all skills in mastery), `augmentAllLevel` (+N to all skills), `itemSkillName` (granted skill), `modifiedSkillName1..N` + `modifierSkillName1..N` (skill modifiers). `petBonusName` is dropped by `extractStats` (no regex match) — pets stay out of scope; list as an exclusion.
- **Save-side reality check (both real characters + transfer stash, 161 items):** `modifierName` appears only as crafting bonuses (`lootaffixes/crafting/…` — two of the four found are *resist* bonuses, so their stats matter), `relicBonus` holds real completion bonuses, `transmuteName` is empty everywhere (confirmed skippable), and no awakened/ascended content yet — but both resolve through existing paths when they appear.
- Augment applicability is per-slot boolean fields on the `ItemEnchantment` record (`head`, `chest`, `legs`, `feet`, `hands`, `shoulders`, `waist`, weapon-type and jewelry booleans — enumerate at implementation); `factionSource` (e.g. `User8`) ties into the faction table, `itemCost` is the iron price.
- The difficulty resistance penalty is **engine-hardcoded, not in data**: Normal/Veteran 0, Elite −25, Ultimate −50 (applies to the damage resistances; the 80 cap applies *after* the penalty, so being capped on Ultimate takes 130 raw; hard cap 95 via +max-resist items).

## Deliverables

- **DB build additions** (bump `DB_SCHEMA_VERSION`; cache rebuilds once):
  - Index `records/skills/playerclass*` + `records/skills/devotion/` + one-hop `buffSkillName` targets into `DbSkill { record, name?, class, tier?, maxLevel, ultimateLevel, cooldown?, duration?, stats }` where leveled stats keep their arrays.
  - Set records: `DbSet { record, name, members, bonusAtPieces(n) }`; link from `DbItem.setName` (already localized) to the set record.
  - Affix stats: extend the affix map to `{ name?: string; stats: Record<string, …> }`; keep `getAffixName`/`knowsAffix` semantics intact. This also covers completion-bonus records (same `LootRandomizer` class).
  - Index one-hop `itemSkillName` targets of items (granted skills — name only).
  - A **skill name map** covering all of `records/skills/` (record → localized name + Class, nothing else — cheap) so any `+N to <skill>` / "Modifies: <skill>" reference renders as a name, never a raw path. Full leveled stats only for: playerclass\*, devotion, one-hop `buffSkillName` targets, and the `skillmodifiers` records items/affixes reference (so an awakened item's modifier payload is renderable).
  - `GameDb` additions: `getSkill(record)`, `getSet(record)`, `getAffix(record)`, `skillName(record)`.
- **Resolver additions** (`resolve.ts`): resolve `ItemInstance.relicBonus` through `getAffix` and carry it on `ResolvedItem` (component/relic completion bonus); carry the granted-skill name for relics/components that have one.
- **Recipe additions**: extend `DbRecipe` with `reagents: { record, name, quantity }[]`, `baseReagent?` (the item consumed, for upgrade recipes), and `ironCost` — this is what lets the advisor check *affordability* of any CRAFT verdict and detect "an awakened version of this item exists" for HOLD reasoning. Keep `ItemAscensionFormula` out of `recipes()` (it crafts nothing specific); it needs no representation beyond the game-rules note that ascension is random.
- **`src/core/mechanics/aggregate.ts`**:
  - `resistanceMatrix(resolved, save, db, difficulty)` — one row per source, each separately attributable so swap deltas are computable: every equipped slot (base / affixes / component incl. its completion bonus / augment as distinguishable contributions), active set bonuses, each counted skill or devotion node. Columns: Physical, Pierce, Fire, Cold, Lightning, Acid/Poison, Vitality, Aether, Chaos (secondary resists — stun, slow, freeze, petrify, life/energy leech — as a footnote list). Summary bands:
    1. **Permanent** — items + affixes + components + augments + set bonuses + passives + toggled auras + devotion passives.
    2. **+ Maintainable** — self-buffs with `duration ≥ cooldown` (Pneumatic Burst et al.). The community counts these (grimtools does when toggled); they are reported as a separate band so the advisor can flag holes that *depend* on them.
    3. **Effective vs cap** — after the difficulty penalty, against the 80 cap, with overcap shown.
  - **Effective skill ranks**: per pointed skill, learned + summed equipped `+skills` bonuses (rule above), clamped; all rank-dependent stats (buff resistances in the matrix, skill lines in the doc) are evaluated at the *effective* rank. Caveat to state in output: a proposed gear swap that changes +skills shifts ranks — the baseline is computed for the current loadout, and the advisor is told to mention rank effects when a swap carries +skills.
  - A **defense summary** beside the matrix: total armor (sum across pieces; note the per-piece absorption approximation), shield block chance/amount when a shield is equipped, and notable sustain (ADCtH presence) — the advisor's "defensive skeleton" beyond resistances.
  - Excluded and listed as exclusions in the output: circuit breakers (`Skill_PassiveOnLifeBuffSelf`), on-hit/proc buffs, potions/consumables, party buffs, item-granted skills (v1 approximation), item skill-modifiers' stat effects (named but not summed), pet bonuses.
  - `damageProfile(...)` — % damage modifiers summed by damage type across the same permanent sources, flat-damage presence, top skill point sinks, resist-reduction sources (the negative-debuff records above), and **damage conversion lines** (source, from→to, %) from gear and skills — conversion redefines a build's effective damage type, and a profile that ignores it misranks the build. Output: ranked damage types — this is what tells the advisor the build is pierce/bleed.
- **CLI** `aggregates --char <name> [--difficulty d]` printing both tables — debug artifact and the verification gate.
- **Tests**: buff classification (Pneumatic Burst → maintainable; toggled aura → permanent; Night's Chill → excluded/RR), rank-array indexing incl. clamp, the +skills effective-rank fold (incl. the ≥1-point rule and the ultimate clamp), weapon-whitelist exposure, set bonus at piece counts, affix stats exposure, matrix summation on a synthetic loadout, schema bump invalidates the cache.

## Acceptance criteria

1. `npm run cli -- aggregates --char _Suchka` prints a resistance matrix whose per-slot rows and band totals hand-check against 2–3 items on grimtools, and whose skill rows put Pneumatic Burst (+ its taken modifiers) in the maintainable band at the **effective-rank** values (invested + gear +skills, clamped at ultimate).
2. The damage profile ranks the character's actual top damage types (expected pierce/bleed here).
3. Every excluded source category is *listed* as excluded in the output — silent omission is how item-only sums mislead.
4. Cache rebuilds exactly once after the schema bump; size growth is modest (skills are a fraction of the item table).
5. `npm test` + `npm run typecheck` green.
